> 今日概念在知识树中的位置：S7-01 让 **run** 能 **暂停、续办**；S7-02 在 **写操作前** 加了 **审批闸**——**老周点头，货才能出**。灰度第四周，**澄光制造** 又来电：**「主管批了，仓库说 **没收到拣货指令**；张工点 **重试**，会不会 **发两遍**？」** 今天拆 **工具失败重试与补偿**：办事链上 **某一步 tool 超时/报错**，产品要定义 **重哪一步、幂等怎么防双写、部分成功怎么补、失败要不要回滚**——**不是接口层无脑 retry 三次**。

### 场景白板（读故事前 30 秒）

- **本集入口**：**应用 B｜修小言**——**张先生** 走 **报修 + 备件出库** 办事链；**老周** 已在 S7-02 场景里 **批准出库**；**阿梅** 盯客户工单。
- **504 / 超时**：白话：**下游系统（如 WMS 仓库）没在规定时间内回话**——对 Agent 来说 **这一步算失败**，但 **对方可能已经处理了一半**。
- **幂等（Idempotency）**：白话：**同一业务动作重复提交，结果和只做一次一样**——靠 **`idempotency_key`**（幂等键，通常绑 `run_id + step`）让仓库 **认「还是这一单」**，别 **拣两遍货**。
- **补偿（Compensation）**：白话：**前面某步其实成功了，后面却挂了**——不能假装没发生，要 **补通知、补状态、或显式撤销**（能撤的话）。
- **本集冲突**：**审批已通过**，**`notify_warehouse` 返回 504**；张先生点 **「重试拣货」**，系统若 **从头跑整条链**，可能 **双出库**；若 **不重试**，车间 **一直等不到滤芯**。

## 寓言故事

### 一、红灯变绿了，仓库却没动

S7-02 审批闸在 **澄光制造** 跑顺之后，张先生以为 **「等老周点头」** 就是最后一关。

周三上午，他对 **AI 小言** 又提了一次 **CF-220 滤芯换芯 + 送车间 B**。**RUN-CG-20260918-024** 照例展开步骤条：

```text
① 识图 …… ✓
② 查质保 …… ✓
③ 查库存 PM-8842 …… ✓
④ 建工单 XR-0918-088 …… ✓
⑤ 备件出库申请 …… ✓（待审批）
```

老周在飞书点了 **批准**。步骤 **⑤** 变绿，**`approval_id=APR-0918-031`** 写入 trace。

然后 **⑥ 通知仓库拣货** 转圈 **三十八秒**，步骤条 **突然变红**：

> **备件系统响应超时（504）**。工单与出库申请已保留；**仓库是否已收到指令不确定**。

张先生愣住：**「老周都批了，怎么还卡？」** 界面给两个按钮：**「重试通知仓库」**、**「联系真人支持」**。

他先点了 **重试**。

十秒后，界面又绿了一瞬：**「已重新通知仓库拣货。」** 张先生去吃饭，心想总算办完。

下午，澄光 **仓库班长小刘** 在群里 @ 设备部：**「**PM-8842 今天怎么来了 **两笔拣货单**？同一 run、同一地址，**差二十分钟**。第二笔谁下的？」**

同时，车间 B 班组长打电话：**「滤芯早到了，你们怎么又派人来送一趟？」**

IT **真人支持** 按惯例在星尘侧建单，标题：**「修小言重试拣货疑似重复出库」**。附：run 截图、两张 WMS 拣货单号、老周批准记录。备注：**「用户张工反馈 **审批后重试**；仓库 **双单**。」**

林薇收到 @，和小陈 **初判**：**不是审批闸失效**（`approval_id` 只有一次）；**是 step_6 失败后的 **重试策略** 错了**——**可能 **重复调了写接口**。

### 二、504 不是「没发生」，是「不知道发生没有」

周四会诊：林薇、阿梅、小陈、大刘（WMS 对接），澄光 IT 与 **真人支持** 坐席在线。

小陈把 **RUN-CG-20260918-024** 的 trace 按时间轴摊开：

```text
14:08  step_5 create_shipment_order(idempotency_key=run_024_ship)
      → OK, shipment_id=SHP-8842-0918-A
14:08  approval APR-031 → approved
14:09  step_6 notify_warehouse(shipment_id=SHP-8842-0918-A)
      → HTTP 504, 无 response body（客户端超时）
14:11  user_action=retry_step_6（同一 run）
14:11  step_6 notify_warehouse(shipment_id=SHP-8842-0918-A)  ← 未带幂等键
      → OK, pick_list_id=PK-002
```

大刘调出 WMS 日志，脸色尴尬：**「**第一次 504 **是我们网关 **回包慢了**——**拣货单 PK-001 其实 **14:09:47 已生成**；你们 **14:11 又打了一次 **创建拣货**，WMS 当成 **新指令**，出了 **PK-002**。」**

阿梅转述小刘原话：**「不是不让重试，是 **重试得让我们知道 **还是同一笔**。」**

张先生在工单备注里写：**「我以为 **红的就是没办成**——绿了一下我就信了。谁知道仓库 **早就动了**？」**

林薇在白板上把 S7 三篇串成一条线：

```text
S7-01：办到哪、别双工单（建单幂等）
S7-02：写之前谁批（审批闸）
S7-03：某步挂了，重试别双出库（步级幂等 + 不确定态）
```

**「问答时代，**答错 **可以下一条覆盖；办事时代，**超时 **可能是 **已成功但没告诉你**。** 审批闸解决 **该不该做**；今天解决 **做了没、要不要再做、做错了怎么补**。」** 她说。

小陈补了一刀：**「`retry_step_6` 实现成 **重新 POST 创建拣货**——**没有 **先查状态**，也没有 **幂等键**。** step_5 的出库单 **幂等了**，step_6 **没幂等**。」**

### 三、账小言那边：半张表进了，整张没进

林薇让苏姐在会诊里投 **账小言** 的对照屏——**澄光** 同租户上周一笔 **对账入账**：

```text
RUN-ZH-20260912-007（账小言）
step_1 拉 MES 产量 …… ✓
step_2 拉 PLC 读数 …… ✓
step_3 生成对账差异 JSON …… ✓
step_4 importReconciliation（写 ERP）…… ✗ ERP 返回 503
```

**财务接口人周会计** 点了 **重试**。第二次 **importReconciliation** 成功——月底关账时发现 **ERP 里 **同一批次入账两条**，差额 **¥12,400 重复**。

苏姐说：**「和仓库 **同一类病**：**写操作 tool **超时**，人以为 **没写上**；**重试** 若不带 **`idempotency_key=run_007_import`**，**财务系统不认 **还是同一 run**。」**

林薇点头：**「报修链 **怕双发货**；入账链 **怕双记账**。** 机制同一套：**步级幂等、先查后写、补偿表**。」**

### 四、双轨落地：重试与补偿怎么写进产品

林薇提交 **《修小言 / 账小言 工具失败重试与补偿双轨方案》**。

**标准 / 规范流程（多系统对接、写操作多、审计要求高）**

| 层级 | 做什么 |
|------|--------|
| **失败分类** | 每步 tool 标：**可重试（瞬态）** / **不可重试（业务拒绝）** / **结果不确定（超时、断连）**——**不确定态禁止直接「再 POST 一次」** |
| **步级幂等** | 所有 **写操作** 带 **`idempotency_key`**（建议 `run_id + step_name`）；下游 **WMS/ERP** 约定 **同键返回同一业务单号** |
| **先查后写（Read-before-Retry）** | 重试前调 **`get_shipment_status` / `get_import_status`**；若已成功 → **标记 step 完成**，**不重复写** |
| **不确定态处理** | step 进入 **`unknown`**（或 `succeeded_uncertain`）；UI **禁止写「已成功」**；给用户 **「系统确认中」+ 自动轮询 + 超时转人工** |
| **重试策略** | **步级重试**（只重失败步），**禁止默认整条 run 重跑**；**指数退避** + **最大次数**；**超过** → run **`failed` 可续办** 或 **转人工** |
| **部分成功** | run 支持 **`partial_done`**：例如 **工单已建、拣货未确认**；**每步 output 持久化**，续办 **从失败步开始** |
| **补偿事务** | 对 **不可简单幂等** 的链（已发货无法自动删单）：维护 **补偿 tool**（`cancel_pick_list`、`reverse_import`）+ **人工审批**；**Saga 思维**——**能补偿的写补偿，不能补偿的锁人工** |
| **与审批闸联动** | **同一 `approval_id` 只消费一次**；重试 step_6 **不再要老周批**——**批准的是出库意图**，不是 **每一次 HTTP** |
| **可观测** | trace 记 **`attempt` 次数、下游返回码、幂等键、查询补单结果**；告警 **双单率、不确定态停留时长** |

**中小常用默认方案（星尘当前可卖）**

- **「三步重试口诀」**：**先查状态 → 再决定补写还是标完成 → 绝不整条链重跑**。  
- **「写操作必带键」**：`create_ticket`、`create_shipment_order`、`notify_warehouse`、`importReconciliation` **统一绑 `run_id+step`**——**先覆盖 80% 双写**。  
- **「不确定就黄灯」**：504/超时 → step **黄色「确认中」**；后台 **每 30 秒查一次**，**最多 5 分钟**；仍不明 → **转真人支持**，卡片带 **run 链接 + shipment_id**。  
- **「用户两个按钮」**：**「重试本步」**（走先查后写）+ **「联系支持」**；**隐藏「从头再来」**（除非用户显式 **取消本 run 新开**）。  
- **「固定话术」**：**「出库申请已批准；正在与仓库确认拣货状态，请稍候。** 未确认前请勿重复申请。」**  
- **可暂缓**：完整 **Saga 编排台**、自动 **跨系统对账补偿**、与 **客户消息队列** 双向订阅——等 **双单/双账 ≥ 月级** 或 **合同写数据一致性条款** 再上。

阿梅问澄光：**「仓库希望张工看见什么？」**

小刘回复：**「**一张单号 **就行；要是系统还在查，**别让他再点出一个新单**。」**

### 五、接近结尾：批准之后，拣货可以断，不能响两回

方案灰度两周后，张先生再走 **换芯发货**。**RUN-CG-20261002-031** 在 **⑥ 通知仓库** 再次 **504**。

这一次界面 **没有立刻变红**，而是 **黄色**：

> **正在与仓库确认拣货状态（已用时 12 秒）……**  
> 出库单 **SHP-1031-A** 已创建；**审批已生效**。请勿重复提交。

后台 **先查后写**：`get_pick_status(shipment_id)` 在 **第十五秒** 返回 **`pick_list_id=PK-031` 已存在**——trace 把 step_6 标 **✓**，**没有第二次 POST**。

张先生界面更新：

> **⑥ 仓库已接收拣货指令（PK-031）**  
> 预计 **今日 16:00 前** 送达车间 B。

老周在群里说：**「这次 **卡了一下**，但没 **多出一笔预算**。」**

对照 **账小言**，周会计那边 **ERP 503** 后，系统 **自动用同一 `idempotency_key` 查询**——发现 **第一次其实已成功**，界面提示 **「入账已完成，无需重试」**，**没有双账**。

林薇在复盘里写 S7 第三句人话：

**「办事链上的橡皮筋：**审批 **决定 **能不能弹**；**重试与补偿 **决定 **弹断了会不会 **弹两次**。** 超时不是零，**是 **「我不知道」**——产品要把 **不知道 **做成 **可查、可等、可转人**，不是 **再猛按一次按钮**。」**

小陈把字段写在角上：**`step_status=unknown` · `idempotency_key` · `compensating_action`.** 阿梅补：**「演示里 **失败很少**；值班要 **假设每一步都可能 **半成功**。」**

张先生回访：**「黄灯比红灯诚实——**至少我知道 **系统在问仓库**，不是 **让我瞎点**。」**

## 概念正解

**工具失败重试与补偿（Tool Failure Retry & Compensation）** 指：在 **Agent 办事链** 中，当 **某一步 tool 调用失败、超时或结果不确定** 时，产品必须定义 **重试边界**（重哪一步、几次、间隔）、**幂等机制**（同一业务动作重复提交不双写）、**不确定态处理**（先查下游真实状态再决定补写或标完成），以及 **补偿路径**（部分成功时如何补通知、撤销或转人工）——**不是** HTTP 客户端 **无脑 retry 三次**，也 **不是** 用户一点「再试」就 **整条 run 重跑**。

回扣故事：S7-02 **审批通过后**，`notify_warehouse` **504**——WMS **其实已建拣货单**；无 **步级幂等 + 先查后写** 的 **重试** 导致 **双拣货**；账小言 **importReconciliation** 同理 **双入账**；双轨方案用 **失败分类、idempotency_key、unknown 态、步级重试、部分成功、补偿 tool** 把 **「重试」** 从 **「再调一次接口」** 升级为 **「可预期的办事续办」**。

在 **S7 · Agent 从演示到值班** 中的位置：**上线专题**——run 与审批闸就绪后，**真实对接** 必然遇到 **瞬态失败与半成功**；本篇补 **数据一致性** 与 **用户可理解的重试**；下一篇 **人工接管** 会处理 **自动重试耗尽仍卡住** 时 **谁接、接后能改什么**。

在 **AI 产品岗** 的典型场景：

| 场景 | 具体例子 |
|------|----------|
| **需求文档** | 每个写操作 tool 写 **幂等键规则、失败分类、重试上限、不确定态 UI、补偿/撤销流程** |
| **方案评审** | 问：**504 后先查还是先写？** 整条 run 重跑是否 **物理禁止**？**approval_id** 重试时 **是否复用**？ |
| **指标设计** | **步级重试成功率、不确定态解析时长、双单/双账率（应为 0）、补偿调用次数、人工接管前平均重试次数** |
| **跨团队沟通** | 对 WMS/ERP：**幂等键契约与查询接口**；对客服：**转人工时带 run_id + 下游单号**；对财务：**入账重试与审批闸的分工** |

## 类比锚定

| 你熟悉的 PM 旧经验 | 工具失败重试与补偿 |
|--------------------|-------------------|
| 支付 **「处理中」** 先查单再决定是否重付 | **超时 → unknown → 查下游状态** |
| 订单 **防重复提交按钮** + **幂等号** | **`idempotency_key=run_id+step`** |
| 发布失败 **只回滚变更步**，不 **重装整个集群** | **步级重试**，不 **整条 run 重跑** |
| 物流 **「已揽收」与「未揽收」** 以网点扫描为准 | **以 WMS/ERP 查询为准**，不以 **HTTP 回包** 为唯一真相 |
| 财务 **冲正 / 红字** 处理错账 | **补偿 tool** 或 **人工冲销** |

## 类比边界说明

### A. 概念核心要点

1. **失败分三类**：明确失败、明确成功、**不确定**——**不确定绝不能当失败直接再写一遍**。  
2. **重试粒度是 step，不是 run**：已成功步 **不重复**；**审批结果** 不因 **通知仓库失败** 而作废。  
3. **写操作必幂等**：键要 **业务系统认**；**同键返回同单号**，不是 **只在自家 DB 去重**。  
4. **部分成功是常态态**：run 要有 **`partial_done`**；用户看见 **「单已建、货待确认」**，不是 **全红或全绿**。  
5. **补偿优于假装没发生**：能 **查单、能撤销、能冲正** 的写进产品；**不能自动撤** 的 **锁人工 + 留 audit**。

### B. 类比失效点

| 失效 | 为什么不能照搬 |
|------|----------------|
| **「像接口重试三次就行」** | 写操作 **第三次可能成功两次**；**幂等 + 先查** 优先于 **次数** |
| **「和数据库事务回滚一样干净」** | **跨 WMS/ERP** 无单库事务；**Saga / 补偿** 是 **业务约定**，不是 **ACID 自动回滚** |
| **「用户点重试 = 新 run」** | 新 run 可能 **重复审批、重复建单**；默认 **续办同一 run 的失败步** |
| **「失败就转人工，不用做幂等」** | 人工也怕 **双单**；**接管前** 系统应 **查清下游状态**，减少 **客服背锅** |

## 本集 Checklist

**标准 / 规范流程**

- [ ] 每步 tool **失败分类**（可重试 / 不可重试 / 不确定）  
- [ ] **写操作** 统一 **`idempotency_key`**；与下游 **契约测试**  
- [ ] 重试前 **先查下游状态**（Read-before-Retry）  
- [ ] **步级重试**；**禁止默认整条 run 重跑**  
- [ ] **`unknown` 态** + 自动轮询 + 超时转人工  
- [ ] **`partial_done`** 与 **每步 output 持久化**  
- [ ] **补偿 tool** 或 **人工冲销流程**（能撤的写撤）  
- [ ] **审批结果** 与 **通知重试** 解耦；**同一 approval 不重复消费**  
- [ ] 监控 **双单/双账率、不确定态时长、重试次数分布**  

**中小常用方案**

- [ ] **写操作必带键**（`run_id+step`）  
- [ ] **504 → 黄灯确认中** + 后台轮询  
- [ ] 用户 **「重试本步」** + **「联系支持」**；隐藏无脑 **从头再来**  
- [ ] **固定话术**：「正在与 XX 系统确认，请勿重复提交」  
- [ ] 账小言 **入账** 与报修 **出库** 共用 **幂等组件**  

**何时升级到完整版**

- **双单/双账** 仍出现；需 **Saga 编排、自动补偿、MQ 对账**；**跨 ≥3 个外部系统** 的长链；与 **人工接管**（S7-04）联动 **重试耗尽** 路径。
