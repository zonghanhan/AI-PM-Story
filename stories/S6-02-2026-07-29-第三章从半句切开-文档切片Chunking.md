## 寓言故事

### 一、权限修好了，答案却只剩半句

澄光制造的检索 ACL 上线两周后，**越权引用** 工单确实没了。王姐在客户成功周报里写了一句：**「档案室门锁好了。」**

第三周周一，IT 服务台又建了一张单——这次不是「看见了不该看的」，而是 **「该看的没看全」**。

李女士问：**「哺乳假可以请多少天？需要提前多久申请？」**

**AI 小言** 回复很克制，只有两条，脚注 [1] 指向《澄光制造员工休假管理办法（2025 版）》：

> [1] ……年假可 **顺延至次年 3 月 31 日前** 使用；**哺乳假相关**……

李女士在工单里圈出后半句：**「前面讲哺乳假天数和提前申请的那半页呢？脚注跳进去，PDF 在第三章中间——** 上一页结尾是『年假顺延』，下一页开头才是『哺乳假』。** 小言像只念了换页处那一刀切下来的尾巴。」**

服务台坐席备注：**「用户确认 ACL 问题已解；本次投诉 **答不全 + 出处定位怪**。请星尘侧看 **知识库入库 / 切片**。」**

林薇把工单转给值班研发小陈，附内部备注：**「请复现并初判；若仅单文档可 **先重切该 PDF**，别动全库。」**

---

### 二、阿寻捞到的，是「断章」

小陈调了检索日志。李女士那次提问，阿寻实际返回的 Top 段里，**相似度最高** 的正是 [1] 对应那一块——块内文本从「……3 月 31 日前」起笔，**哺乳假天数** 在 **下一块** 里。

他在文档里画出示意图：

```text
《休假管理办法》第三章（PDF 第 12–13 页）
┌─────────────────────────────────────┐
│ ……年假可顺延至次年 3 月 31 日前使用。  │  ← 块 A 结尾
├────────── 固定 512 Token 切刀 ────────┤
│ 哺乳假：子女周岁内，每日 1 小时……      │  ← 块 B 开头（天数、申请时限在这里）
│ 须提前 3 个工作日向直属主管……          │
└─────────────────────────────────────┘
```

**「李女士问的是哺乳假，向量检索命中了块 A 里残留的『哺乳假相关』四个字——** 块 A 的主体其实在讲年假顺延 **。Rerank 没救回来，因为块 B 单独看又没那么像用户原句。」**

林薇问：**「飞书里整份 PDF 是完整的，为什么进库就断了？」**

小陈：**「当时为了赶澄光首版上线，用的是平台默认 **固定长度切片**：每 512 Token 一刀，**重叠 50 Token**。没读 PDF 的 **章节标题**，也没按 **第三条、第四条** 边界切。」**

他又补了一个对照：**「商小言那边有个商家投诉更直观——** 退货条款第 7 款 **被切成两半，一半在『七日内』，一半在『定制商品除外』。客服小言只引了前半，买家以为定制也能退。」** 那是 **应用 A** 的工单，根因同一类：**切法不认结构**。」

### 三、三种骂法，一套尺子

下午评审，林薇把 **澄光王姐**、**商小言客户成功阿梅**、算法同学拉进飞书会议。没有人说「这是模型笨」——三张截图摆在一起，骂法却不一样：

| 谁 | 要什么 | 嫌什么 |
|----|--------|--------|
| **李女士（员工）** | 一次答清哺乳假天数 + 申请时限 | 答案像 **剪报边角**；脚注跳进章节中间 |
| **王姐（HR）** | 对外答复能写「见办法第三章第 2 节」 | 库里一段混着 **年假 + 哺乳假**，审计时对不上 **制度条文编号** |
| **商小言商家运营** | 买家问退货，**整段政策进上下文** | 固定切刀把 **「除外」** 切到下一页，**AI 小言** 只引到利好半句 |

算法同学在白板上写：**「切片不是越碎越聪明。碎，是为了 **检索能命中**；但不能碎到 **语义和结构对不上**。」**

他们归纳了三条产品尺子：

1. **检索尺子**：一块里是否 **只讲一件事**（一个制度条、一个 FAQ、一个故障码）？  
2. **出处尺子**：脚注能否对应 **章节 / 页码 / 源文档锚点**，而不是「第 37 号碎片」？  
3. **权限尺子**（回扣 S6-01）：一块是否 **继承文档 ACL**，且 **不会把公开段和 HR 专属段粘在同一块**？

王姐愣了一下：**「上次 ACL 是 **谁能看见**；今天是 **看见了但缺一半**？」**

林薇点头：**「两回事，但 **入库时就要一起想**。切太粗，检索捞不准；切太碎或切错边，**权限标签和章节标签** 都会糊。」**

### 四、先结构，再长度；先能运营，再谈优雅

小陈拿出 **文档切片 / Chunking** 方案——不是单一参数，而是一套 **策略选择**。

**标准 / 规范流程（多库种、强合规、可回放）**

| 策略层 | 做什么 |
|--------|--------|
| **结构感知** | PDF/Word/Markdown **先按标题、条款编号、表格边界** 切；**不在句子中间下刀**（除非段落本身超长） |
| **长度兜底** | 单节仍超上限时，再 **按段落二次切**；保留 **overlap（重叠窗）** 避免边界信息丢失 |
| **元数据** | 每块写入 `doc_id、章节号、页码、版本、visibility（ACL 标签）`；脚注展示 **人类可读锚点** |
| **库种分策** | **制度库** 偏结构切；**工单 FAQ** 偏 **一问一块**；**商小言商品说明** 偏 **SKU/条款级** |
| **评测** | 维护 **「切片回归集」**：同一问题，换切法后 **召回条数、完整率、脚注偏移** 是否改善 |
| **重切与版本** | 文档更新 → **新版本切片**；旧索引 **可灰度切换**（下篇再讲延迟） |

**中小常用默认方案（星尘当前可卖）**

- **两档切法**：上传时选 **「制度文档（按标题）」** 或 **「短 FAQ（整段）」**；默认 **禁止纯固定 Token 一刀切** 制度 PDF。  
- **重叠窗**：结构切后再 **块间重叠 10%–15%** 字数，成本低，能缓解 **「换页断句」**。  
- **块上限**：单块不超过 **800–1200 中文字**（或平台 Token 上限的 70%），超长节 **二次切 + 同章标签**。  
- **可暂缓**：自动表格还原、多栏 PDF 版式分析、跨文档 **语义合并**——等客户文档复杂度上来再卖。

会上有争议。阿梅说：**「商家几千条 SKU 说明，谁给每条写标题？」**

林薇：**「那就 **库种分策**——SKU 用 **一行一条** 或 **模板字段切**，别拿制度的刀切货单。中小客户先选 **文档类型**，比开放十个旋钮更能交付。」**

澄光当场拍板：休假办法等 **37 份制度 PDF** 走 **结构感知重切**；李女士原题回归后，脚注 [1] 变为 **「第三章 §3.2 哺乳假」**，答案四条齐全。

### 五、接近结尾：不是库小，是刀法不对

又过十天，澄光 **「答不全 / 出处跳章」** 工单从每周三四张降到 **零星**。运营后台上传页多了一行提示：**「制度类请选择按章节切片；未识别目录时将提醒人工分段。」**

王姐试用 **「以工艺部员工预览检索」** 时，会顺带看一眼 **命中块预览**——每块标题旁印着 **章节号**，她终于能在对内审计里说：**「小言引用的是办法第三章第 2 节，不是向量库第 884 段。」**

林薇给新同学讲 S6 第二课，把 S6-01 的白板往下接了一行：

**「ACL 决定 **李女士能看见哪些块**；Chunking 决定 **每一块是不是一条完整制度、一个完整出处**。RAG 库房里的书，**既不能只把整本扔进去搜不到，也不能撕成废纸屑让脚注对不上页码**。」**

小陈把英文写在旁边：**Chunking strategy。** 李女士后来在 **内小言** 里又问哺乳假，回复底部是 [1] 第三章 §3.2，**天数、时限、申请流程** 一次说完。她在回访里写：**「这次像人事窗口递过来的整页说明，不是复印机卡纸只留下半行。」**

林薇在季末白板 **「知识从哪来」** 那一栏打了个勾——**入库怎么切**，是运营能讲清楚的第一层；**切完还能不能对权限、对出处**，才是能长期值班的前提。

## 概念正解

**文档切片 / Chunking（Chunking Strategy）** 指把长文档拆成 **适合检索与引用的小文本块** 再写入向量库（及关键词索引）的策略与规则集合。它解决的是 **「库里有内容，但捞出来的段不完整、不聚焦、出处对不准」** 的问题：拆得太粗，检索命中率低；拆得太碎或 **无视章节/条款边界**，会出现 **半句话、半条政策、脚注跳进章节中间**。典型做法包括 **结构感知切分**（按标题、编号、段落）、**长度兜底与重叠窗（overlap）**、为每块写入 **章节/页码/版本/ACL 等元数据**，并按 **库种（制度、FAQ、商品说明）** 选用不同策略，配合 **切片回归评测** 迭代。Chunking **不替代** ACL（S6-01），但切法会影响 **权限标签是否准确附着到每一块**；也 **不替代** Grounding（第 11 篇），但块边界决定了 **脚注能否指向人类可读的出处**。

回扣故事：李女士的哺乳假缺半页，是 **固定 Token 切在年假与哺乳假之间**；商小言退货案是 **同一条款被切成两半**；王姐要 **第三章第 2 节** 而非「碎片编号」；澄光 **结构重切 + 重叠窗** 是中小可交付路径，**库种分策** 避免用一把刀切所有文档。

在 **S6 · 知识可运营、权限可审计** 中的位置：本篇锚定 **「知识从哪来」** 的第一道工序——**入库切片**；与 S6-01 的 **「谁能看见」** 衔接（块级元数据与 ACL）；后续 **版本更新、引用展示、投毒对抗** 都假设 **块边界稳定、可运营**。

在 **AI 产品岗** 的典型场景：

| 场景 | 具体例子 |
|------|----------|
| **需求文档** | 写清 **支持的文档类型、默认切法、单块上限、重叠比例、块级元数据字段**；制度 PDF 与 FAQ 是否 **分策略** |
| **方案评审** | 问：**脚注展示用什么锚点？** 更新文档后 **是否全量重切？** 固定长度切 **在哪些库种禁用？** |
| **指标设计** | **答案完整率**（抽检）、**脚注章节偏移率**、**单问命中块数分布**、**切片回归集通过率** |
| **跨团队沟通** | 对运营：**「上传类型选对，比事后改 Prompt 便宜」**；对工程：**「先结构后长度，元数据跟块走」**；对客户成功：**「商家 SKU 库别用制度切法」** |

## 类比锚定

**核心类比：把厚手册裁成便签条放进检索盒——裁得太大块塞不进抽屉（检索不命中），裁得太碎或从一条规定中间剪开（答半句、出处对不上条号）。**

| 你熟悉的 PM 经验 | Chunking 要素 |
|------------------|---------------|
| 帮助中心 **一篇 FAQ 一个页面** | **一问一块 / 一主题一块** |
| 合同 **按「第 X 条」引用** | **结构感知切分 + 章节元数据** |
| 短信 **70 字一条，长文拆多条** | **长度兜底 + overlap 防断句** |
| 商品详情 **规格表按行展示** | **库种分策**（货单 ≠ 制度） |
| 版本发布说明 **v2.3 改了第几节** | **块带 `doc_version`，便于重切与审计** |

## 类比边界说明

### A. 概念核心要点

1. **Chunking 是入库策略，不是模型参数**——切法错了，调 Temperature 救不了 **半条政策**。  
2. **结构优先于长度**——制度、合同、SOP 等 **按章节/条款** 切；固定 Token 仅作 **兜底**。  
3. **块级元数据是运营与合规的接口**——章节号、页码、版本、ACL 标签应 **随块写入索引**。  
4. **库种不同，刀法不同**——内小言制度库、商小言退货 FAQ、修小言故障码 **不能共用同一默认切法**。  
5. **要可评测、可重切**——维护 **切片回归集**；文档更新后 **重切策略** 需产品定义（与下篇「版本延迟」衔接）。

### B. 类比失效点

| 类比说法 | 失效点 | 更准确的理解 |
|----------|--------|--------------|
| 「像网页分段复制就行」 | 网页有 DOM；PDF 多栏、页眉页脚、扫描件 **没有天然段落** | 需 **版式解析或人工分段**；扫描件往往要先 OCR |
| 「切得越碎检索越准」 | 过碎导致 **上下文不足**、**召回噪声多**、**脚注碎片化** | 在 **语义完整** 前提下控制块大小；用 overlap 补边界 |
| 「语义切分一定比规则切好」 | 语义模型 **慢、贵、边界不稳定**；合规场景要 **可解释条号** | **规则/结构为主，语义作辅助**（超长节二次切） |
| 「切一次就永远不用管」 | 源文档改版、ACL 调整、模板变更 都要 **重切或增量索引** | 产品需定义 **版本与重切触发**（S6 后续篇） |

## 本集 Checklist

**标准 / 规范流程**

- [ ] 入库支持 **结构感知切分**（标题/条款/段落），**禁止** 对制度类默认纯固定 Token 切  
- [ ] 每块写入 **章节/页码/版本/ACL** 等元数据；脚注展示 **人类可读锚点**  
- [ ] **库种分策**（制度 / FAQ / 商品说明 / 手册）可配置，而非全局单一参数  
- [ ] 维护 **切片回归评测集**；文档更新触发 **重切与索引切换规则**（与版本策略衔接）  
- [ ] 运营后台 **块预览**（命中时可见章节标题与可见范围）

**中小常用方案**

- [ ] 上传时 **文档类型二选一**（制度按章 / FAQ 整段）+ **10%–15% overlap**  
- [ ] 单块 **800–1200 字** 上限；超长节二次切并保留 **同章标签**  
- [ ] 单客户事件止血：**指定文档手动重切**，不必等全平台发版  

**何时升级到完整版**

- 客户 **多栏 PDF、扫描件、表格密集型** 文档占比高；脚注需对齐 **监管条号**；**跨应用** 统一知识中台；或 **答不全 / 出处偏移** 类工单 **反复出现** 且已排除 ACL 问题。
