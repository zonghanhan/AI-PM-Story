> 今日概念在知识树中的位置：S6-06 用 **金丝雀 + 30 天扫描** 回答了周老板「以前漏过没有」。他接着问：**「下次脚注再闪错，我能不能 **比买家先看见**？」** 星尘侧日志其实不少——向量检索一条、Rerank 一条、生成一条——却 **拼不成同一次问答的「谁引了哪一段」**。今天卡在 **检索与引用可观测性**：不是「有没有日志」，而是 **能不能从用户一句话追到 chunk、从 chunk 追到告警**。

### 场景白板（读故事前 30 秒）

- **本集入口**：**应用 A｜商小言**——**周老板**（木语工坊租户管理员）在 S6-06 跨租户事件后要求 **可自查的引用留痕**；**小敏** 是商家客服，日常用 **AI 小言** 答买家。
- **可观测性（Observability）**：白话：系统跑起来以后，你能 **用统一 trace 看清「刚才发生了什么」**——不只服务器活着，还能回答 **「这次回答引了哪几段、哪一步过滤掉了什么、为何告警」**。
- **归因（Attribution）**：把 **最终答案 / 脚注** 反查到 **具体 doc_id、chunk_id、版本、检索分数、是否进入最终 prompt**——出事时能指到 **某一页纸**，不是「模型说的」。
- **本集冲突**：S6-06 止血后，周老板要 **自己查清「这次回答引了哪几段」**——不能只靠星尘口头解释。

## 寓言故事

### 一、周老板要的不是「再道歉一次」

木语工坊跨租户脚注事件止血后的第三天，周老板没再发火，却把续约附件里的 **「数据与引用审计」** 一栏标了黄。

他在工单里写得很具体：**「请提供：① 任意会话 **引用了哪些知识片段** 可查；② **脚注与最终上下文不一致** 时，**平台先于客服告警**；③ 我方管理员能 **自助导出近 7 天引用明细**，不必每次找你们研发捞日志。」**

林薇把需求转给值班研发小陈：**「不是新功能脑洞，是 S6-06 复盘里 **『坏了怎么发现』** 的下一格。先别答 **『日志都有』**——上次 30 天扫描，你们 **捞了六个小时** 才拼出 cross-hit 清单。」**

小陈回：**「网关有 request log，阿寻有 search log，Rerank 服务有自己的…… **session_id 有时对不上**，脚注 UI 那次闪错，**预览层没记 final_context 版本号**。」**

林薇在内部频道记了一句：**「客户要的是 **可观测**，不是 **有日志」。**」

---

### 二、日志很多，却拼不出「那一秒」

为了评估工作量，小陈拉了一次 **「模拟周老板查账」** 演练。

小敏在测试环境问了句：**「这款餐椅护垫单买多少钱？」** **AI 小言** 回答正常，脚注 [1] 指向木语 **《2025 夏季配件价目》** §2。一切看似干净。

周老板若问：**「昨天下午 3 点 12 分，客服会话 `sess_8f3a` 引了哪几段？」** 工程师要在三个系统里搜：

```text
① API 网关日志     → 有 session_id、tenant_muyu、latency
② 向量检索日志     → 有 query_embedding_hash、top_k=8、collection=rag_prod_v3
                      但 session_id 字段有时为空（异步批处理写入）
③ Rerank 日志      → 有候选 doc_id 列表，无「是否进入最终 prompt」标记
④ 生成服务         → 有 prompt token 数，**未记录引用了哪些 chunk_id**
⑤ 脚注 UI 埋点     → 只记「用户点击了 [1]」，**未记预览层曾加载过哪条 snippet**
```

**「所以 S6-06 那次闪错，我们是靠小敏 **录屏** 才知道预览层读了家加优品 chunk。」** 小陈在白板上画了个断开的链条，**「检索其实 **捞到过**——Rerank 也 **剔除过**——但 **没有一条 trace 把『捞到→剔除→最终引用』串起来**。周老板要的 **自助导出**，现在等于 **让商家管理员会写 SQL 拼三库**。」**

林薇问：**「澄光内小言那边呢？」**

小陈调出 **应用 C** 对照：澄光运营台上周刚上过 **「检索明细」** 试用页——HR 能看 **「小言回答李女士时引了哪份制度、哪一页」**，但那是 **手工埋点 + 每周离线报表**，**实时告警还没有**；和商小言 **共用阿寻内核**，**缺口一样**。

---

### 三、一次「差点又靠录屏」的灰度

讨论还没完，**真人支持** 又转进一条 **P2 候选** 工单。

另一家试点商家 **「禾野布艺」** 客服反映：上午起，**AI 小言** 回答「窗帘定金能否退」时，脚注 [1] **稳定指向已废止的旧版《订购须知 2024》**——正文却写 **「按 2025 版 §4 可退」**，**正文与脚注打架**。没人录到「闪一下」，因为 **错误是稳定的**——比 S6-06 更难发现：**买家若只看正文复制发送，根本不看脚注日期**。

林薇让小陈查 **禾野租户 `tenant_hey` 近 4 小时会话**。小陈 **花了 40 分钟** 才确认根因：

```text
trace 缺失 → 先按时间窗捞检索日志 → 猜 session → 对生成日志
   ↓
发现：阿寻 命中 chunk「订购须知-2024-§3」（status=已废止，但索引未 purge）
   ↓
Rerank 分数低，未进 final_context
   ↓
模型正文依据 system prompt 里的「2025 退定政策摘要」生成 ✓
   ↓
脚注组件仍绑定「检索候选集第 1 条」展示 ✗（与 S6-06 同类 UI 债）
```

**「若有 **完整 trace**，这事 **10 分钟以内** 能定位；若有 **告警规则**——**『废止文档出现在脚注』**——**客服还没转发给买家就该响**。」** 林薇在工单备注里写：**「再次证明：**日志碎片化 = 不可观测**；**靠客服截图 = 观测滞后**。」**

她给周老板回电，没空许诺「下周全做好」，但说了实话：**「您提的三条，本质是 **检索链路与引用链路的可观测性**；我们按 **双轨** 给您排期。」**

### 四、周老板要的不是道歉，是一张能自己查的账本

周四下午，林薇拉上小陈、商小言前端和澄光对口 IT。周老板派来的运营 **小陆** 第一句话很冲：**「你们能不能让我 **自己查** 这次回答引了哪几段？别每次 P1 都等客服截图。」**

林薇没空许诺「下周全做好」，但认了账：**「您要的是 **检索与引用的可观测性**——同一条 **trace_id（追踪号，从提问贯穿到脚注）** 把 **捞了什么、滤掉了什么、最后进了 prompt 什么** 记下来。」**

小陈在白板上画了三层：

```text
检索候选 → 过滤后 → final_context（进 prompt）→ 脚注展示
           ↑                    ↑
      都要能查、要能告警「不一致」
```

大刘问：**「要不要上全链路 APM（应用性能监控，盯每个服务耗时的那种）？」**

林薇摇头：**「中小先 **编排层一条 trace** + **final_context 快照** 就够。全链路 **OpenTelemetry**（分布式追踪标准）和大屏，等告警每周误报太多再上。」**

小陆问：**「告警会不会很吵？」**

林薇：**「先上五条：**跨租户、废止文档进脚注、脚注与正文版本冲突、检索零命中却带脚注、重复引用已下架**。**MTTA**（从告警到值班确认的平均时间）先盯起来，比等买家截图便宜。」**

会上拍板：

| 会上定的 | 白话 |
|----------|------|
| **统一 trace_id** | 检索/Rerank/生成/脚注同一号 |
| **四态账本** | 候选 / 过滤 / 进 prompt / 脚注展示 |
| **租户自助查** | 周老板能导出自己会话引用明细 |
| **脚注只信 final_context** | 接 S6-06，预览层也记账 |
| **T+1 报表也行** | 先周报，再实时 |

### 五、接近结尾：观测是为了比用户先伸手

两周后，木语工坊管理员后台多了 **「引用与检索」** 页——简版，但够用。

小敏周三晚班问完价，小陆在后台按会话 ID 搜到一条记录：

```text
trace_id: tr_muyu_20250815_193204
问题: 「橡木餐桌最低能给多少？」
final_context: [chunk_muyu_price_faq_2025q3 §2]  ← 进入 prompt
footnote_shown: [同上]                             ← 脚注一致 ✓
retrieval_filtered: [chunk_homeplus_floor_xxx]     ← 曾捞到，已剔除，记原因：tenant_mismatch
alert: 无
```

同一晚 21:07，澄光 **内小言** 试点告警：**「废止文档 `cg-leave-2024` 出现在脚注候选」**——值班研发一看 trace，**索引 purge 任务卡住**；HR 还没人问，**先修索引**，比李女士截图早 **一个半小时**。

周老板在续约附件里把黄标去了，留言：**「我要的不是日志文件，是 **出了问题我先知道**。」**

林薇给新同学讲 S6 第七课，把季末白板 **「坏了怎么发现」** 写完整：

**「S6-03 讲 **知识旧不旧**；S6-06 讲 **串没串租户**；今天讲 **出事时你能不能 **指到 chunk、比用户先知道**。检索与引用可观测性 = **trace 串起来 + chunk 记四态 + 租户能查 + 规则先告警**——不是运维炫技，是 **B 端客户敢签审计条款** 的底线。」**

她在 **「知识从哪来、谁能看见、坏了怎么发现」** 三行里，第三行终于从问号改成勾——**但 S6 还没收官**：白板角落还留着 **「有人故意投毒怎么办」** 和 **「越权导出怎么防」**，那是 **上线专题** 的下一两格。

小陈把英文写在旁边：**Retrieval & Citation Observability.** 林薇补中文：**检索与引用可观测性——让每一次「引用了哪一页」，**都能被追问、被告警、被导出**，而不是散落在六个系统里等录屏。**

## 概念正解

**检索与引用可观测性（Retrieval & Citation Observability）** 指在 RAG 问答链路上，用 **统一追踪（trace）、结构化日志、chunk 级归因与主动告警**，让产研与租户能回答：**「这次回答引了哪几段知识、哪几步检索/过滤/重排、脚注是否与最终上下文一致、异常是否在用户扩散前被发现」**。它解决 **「日志很多却拼不出一次会话」「脚注错了靠买家截图才知道」「废止/越权文档 silent fail」** 等问题——核心不是堆砌日志行，而是 **可关联、可查询、可告警、可对外举证**。手段包括：**trace_id 全链路贯穿、检索候选/剔除/final_context/脚注展示四态账本、租户自助引用报表、规则化告警（跨租户、版本冲突、空检索高置信等）、与 Citation UX / 租户隔离联动的指标**。

回扣故事：周老板要 **比买家先看见**——工程师发现 **六处日志对不上 session**；禾野 **正文与脚注打架** 因 **废止 chunk 仍在候选集** 且 **无告警**，靠人工拼 40 分钟；加固后 **trace + 四态账本 + 五条告警**，木语能 **自助查会话**，澄光 **废止文档进脚注** 在 HR 提问前 **先响铃**。

在 **S6 · 知识可运营、权限可审计** 中的位置：补齐季末三板斧之 **「坏了怎么发现」**——S6-01～05 管 **来源与权限与运营**，S6-06 管 **租户外墙**，本篇管 **出事后的可追溯与主动发现**；为 **提示词注入/文件投毒、越权导出** 等对抗专题铺垫 **日志与告警底座**。

在 **AI 产品岗** 的典型场景：

| 场景 | 具体例子 |
|------|----------|
| **需求文档** | 定义 **trace 字段**（session、tenant、chunk 四态）、**租户可见范围**、**告警规则表** 与 **误报处理流程** |
| **方案评审** | 问：**脚注数据写入哪一步？** 废止文档 **索引与告警谁负责？** 商家导出 **是否含他户 snippet？** |
| **指标设计** | **引用不一致率**、**cross-tenant 告警数**、**检索空结果率**、**MTTA / 用户先于平台发现的比例** |
| **跨团队沟通** | 对商家：**「可观测是产品能力，不是售后捞日志」**；对研发：**「先编排层 trace，再谈全链路 APM」**；对法务：**「保留多久、能否举证、如何脱敏」** |

## 类比锚定

**核心类比：快递 **全流程可追踪**——不是仓库门口装一个摄像头就完事，而是 **揽收、分拣、中转、派送** 同一运单号可查；异常（丢件、错分）**系统先预警**，而不是收件人拍照投诉你才查监控。**

| 你熟悉的 PM 经验 | 检索与引用可观测性 |
|------------------|-------------------|
| 接口 **request_id** 贯穿微服务 | **trace_id** 贯穿检索 → Rerank → 生成 → 脚注 |
| 订单 **状态机**（已支付/已发货/已签收） | chunk **四态**（候选 / 剔除 / 进 prompt / 脚注展示） |
| 业务后台 **订单详情页** 自助查物流 | 租户 **引用明细页** 自助查「引了哪段」 |
| 监控 **告警规则**（支付失败率 > 阈值） | **废止文档进脚注、cross-tenant** 等规则告警 |
| 客服工单 **附用户截图** 才查日志 | **平台先于用户发现** 引用异常 |

## 类比边界说明

### A. 概念核心要点

1. **可观测 ≠ 有日志**——要能 **用业务语言查一次问答**，不是让研发 **拼 SQL**。  
2. **归因要到 chunk + 版本**——「引了价目」不够，要 **doc_id、chunk_id、发布态、是否进 final_context**。  
3. **脚注与 prompt 必须可对账**——UI 层观测与 **生成上下文** 观测 **缺一不可**。  
4. **告警服务客户信任**——B 端宁可 **初期误报调参**，不要 **静默错误到买家截图**。  
5. **与隔离、ACL、运营后台联动**——观测数据本身 **受租户边界约束**；导出 **不能变向越权**。

### B. 类比失效点

| 类比说法 | 失效点 | 更准确的理解 |
|----------|--------|--------------|
| 「和 API 监控一样加个大盘就行」 | RAG 异常 **非单一 HTTP 5xx**；**检索空、引用错、版本旧** 都可能是 **200 成功** | 要 **领域告警规则 + chunk 归因**，不是只看 QPS |
| 「全链路 APM 上了就一劳永逸」 | 向量检索 **异步、批索引** 与 **在线问答** 时钟不同步 | **编排层 trace + 离线报表** 常是中小第一步 |
| 「租户能查日志 = 把 Kibana 账号给他」 | 原始日志 **含他户噪声、技术字段、隐私** | **产品化引用报表**，字段 **脱敏 + 租户过滤** |
| 「告警越多越好」 | **告警疲劳** 导致值班忽略真正的 cross-tenant | **五条高信噪比规则起步**，误报 **周级复盘调阈值** |

## 本集 Checklist

**标准 / 规范流程**

- [ ] RAG 全链路 **统一 trace_id**；检索/Rerank/生成/脚注 **同一 ID 可关联**  
- [ ] **Chunk 四态账本**：候选、剔除（含原因）、final_context、footnote_shown  
- [ ] 租户 **自助引用查询/导出**；字段 **脱敏 + 严格 tenant 过滤**  
- [ ] **领域告警规则** 进值班 playbook；与 **P1 隔离事件** 联动  
- [ ] 指标：**引用不一致率、cross-tenant 尝试、检索空结果率、用户先于平台发现占比**  
- [ ] 日志 **保留周期、举证导出、删除权** 与法务对齐  

**中小常用方案**

- [ ] **编排层先落 trace** + **final_context 异步快照**（可 T+1 报表）  
- [ ] **五条高优先级告警** 先上线；脚注 **只信 final_context** 且 **展示写入账本**  
- [ ] 商家 **每周引用 CSV** 优于 **每次 P1 人工捞日志**  
- [ ] 告警误报 **周级复盘** 调阈值，避免疲劳  

**何时升级到完整版**

- 合同写入 **引用审计 / SLO**；**多租户大客户** 要求 **实时自查**；**告警每周 >N 次** 需 **自定义规则**；或平台 **A/B/C/D 共用 RAG** 需 **统一可观测中台**。
