### 场景白板（读故事前 30 秒）

- **本集入口**：**应用 C｜内小言**——澄光制造飞书里的 **AI 小言**；**王姐** 是客户侧 HR 接口人，负责制度上传；**李女士** 是普通员工。
- **知识库版本（KB Versioning）**：同一份制度在系统里可能有 **多个版本号**；检索与脚注应默认命中 **当前生效版**，旧版 **下架或标记废止**。
- **更新延迟（Update Latency）**：文件上传成功 ≠ 立刻可检索——中间还有 **解析、切片、向量化、索引同步**；用户感知的「已发布」与工程上的「可检索」往往 **差几分钟到几小时**。
- **本集冲突**：王姐 **上传成功**，李女士问到的仍是 **旧版哺乳假**——脚注也指向 **2025 版**，不是 **2025.8 版**。

## 寓言故事

### 一、上传成功，员工看见的却是旧纸

澄光制造把《员工休假管理办法》从 **2025 版** 修订到 **2025.8 版** 的周五下午，王姐在 **内小言运营后台** 点了「替换上传」，文件名旁很快出现绿色对勾：**「上传成功。」**

她在群里通知各部门：**「下周一按 8 月版执行，哺乳假天数有调整，大家问小言就行。」**

周一上午九点十七分，IT 服务台建了一张工单。李女士截图里，**AI 小言** 答得很有礼貌，脚注 [1] 清清楚楚：

> **来源 [1]**：《澄光制造员工休假管理办法（2025 版）》第三章 §3.2 哺乳假——**每日 1 小时，合并使用不得超过 1 小时/日**……

李女士附言：**「王姐说 8 月版改成 **每日 2 小时、可合并为 1 次 2 小时** 了。小言怎么还在念旧版？脚注也是 2025 版，不是 2025.8。」**

服务台坐席备注：**「HR 确认后台已上传；用户侧检索仍命中旧版。请星尘看 **知识库版本 / 索引更新**。」**

林薇把工单转给值班研发小陈，内部备注：**「非 ACL、非切片半句——疑似 **旧索引未下线** 或 **新版未入检索**。请复现并初判；若仅澄光单库，**先查该 doc 版本链**，别动全平台。」**

---

### 二、库房有两排架子，阿寻还在摸旧排

小陈拉了一条李女士提问时的检索日志。阿寻返回的 Top 段里，**相似度最高** 的块元数据写着：

```text
doc_id: cg-leave-2025
version: 2025.0
effective_to: null          ← 旧版未标记废止
chunk_id: cg-leave-2025-ch-042
indexed_at: 2025-07-12 03:11
```

而王姐周五上传的文件，在 **对象存储** 里已经有了：

```text
doc_id: cg-leave-2025        ← 同一个 doc_id
version: 2025.8
uploaded_at: 2025-08-01 16:42
pipeline_status: SUCCESS     ← 后台显示「处理成功」
```

**「矛盾不在模型，在 **版本状态机**。」** 小陈在飞书文档里画了一条线：

```text
王姐点「上传成功」
        ↓
   文件落盘（秒级）
        ↓
   解析 → 切片 → 向量化 → 写入向量库   ← 通常 3–15 分钟
        ↓
   旧版 chunk 是否标记废止 / 从检索池剔除？  ← 澄光没开，默认「并存」
        ↓
阿寻检索：新旧两块都像「哺乳假」，旧块历史命中多、向量更近 → 仍排第一
```

林薇问：**「所以王姐看见的绿色对勾，只是 **文件收到了**？」**

小陈点头：**「对。她们以为 **对勾 = 员工明天就能问到新版**；我们后台 **处理成功** 也只表示 **新块进库了**，没表示 **旧块下架了**。」**

他又补了一个 **应用 A** 的对照：某商小言商家 **双 11 前夜改价目表**，运营后台同样显示上传成功；买家问「这款还参与满减吗」，**AI 小言** 引的仍是 **上周缓存里的活动页**——客服在工单里写：**「价目是新的，回答像旧的。」** 根因同类：**版本策略 + 生效时间 + 索引切换** 没产品化。

---

### 三、三句人话，三种「发布」

下午林薇拉了个短会：澄光王姐、小陈、负责 **阿寻** 的算法同学。王姐有点急：**「切片你们修好了，为什么 **旧纸还在架上**？」**

林薇没急着甩英文，先把 **三种「发布」** 写在白板上——她说这是 HR 和 IT 最容易各说各话的地方：

| 谁眼里的「发布了」 | 实际意味着什么 | 员工能感知到吗 |
|--------------------|----------------|----------------|
| **王姐：上传成功** | 文件进入待处理队列 | **不能**——最多知道「交了」 |
| **后台：处理成功** | 新版 chunk 已写入索引 | **不一定**——旧版可能还在检索池 |
| **产品：对外生效** | 检索默认只命中 **当前生效版**；脚注展示 **版本号 + 生效日** | **能**——这才是李女士该看见的 |

算法同学补了一句：**「向量检索不会自动懂 **8 月版取代 7 月版**。你不告诉它 **哪一版算数**，它就按 **相似度** 挑块——旧块若措辞更接近历史问法，还会 **占着第一名**。」**

他们归纳出 **知识库版本与更新延迟** 要同时管的两件事：

1. **版本（Versioning）**：同一 `doc_id` 下多版如何 **编号、谁生效、旧版何时废止**；脚注能否写出 **「2025.8 版 §3.2」** 而不是含糊的「2025 版」。  
2. **延迟（Latency）**：从上传到 **可检索** 要多久；这段时间 **用户问到了怎么办**；是否允许 **定时生效**（如「8 月 1 日 0 点切换」）。

王姐愣了一下：**「所以我们一直缺的不是 **再传一次**，是 **传完之后系统怎么换架子**？」**

林薇：**「对。S6-01 管 **谁能看见**；S6-02 管 **怎么切**。今天管 **哪一版、什么时候换上去**。」**

---

### 四、会上先对三种「发布」，再谈能等多久

小陈把 **李女士旧版脚注** 和 **王姐绿色对勾** 并排投屏。林薇：**「矛盾不在模型，在 **版本状态机**——上传成功只是货车进厂，换架下架还没做完。」**

王姐：**「能不能我先 **预览** 一眼，确认小言答的是 8 月版，再通知全员？」**

林薇：**「可以——**草稿预览**；中小哪怕先做 **仅上传者 + HR 可检索**，也比全员先踩雷。」**

小陈：**「中小默认 **替换即生效**：同 `doc_id` 新版处理成功后 **自动废止上一版**；上传页显示 **已上传 / 索引中 / 已生效**，别让用户以为对勾 = 明天就能问到。」**

大刘：**「客户 WMS 中午批处理慢是常态——制度类可以书面 **P95 15 分钟**；未生效前 **AI 小言** 提示『知识库更新中』。」**

会上拍板：

| 会上定的 | 白话 |
|----------|------|
| **版本链** | doc_id 固定，version 递增，生效/失效日 |
| **旧版废止** | 退出默认检索，审计可只读 |
| **流水线状态可见** | 别通知早了 |
| **脚注带版本号** | 方便 HR 肉眼核对 |
| **单文档强制刷新** | 澄光止血用 |

澄光拍板：休假办法 **替换即生效 + 进度状态**；李女士回归，脚注 **2025.8 版 §3.2**。

---

### 五、接近结尾：不是没传，是换架没写完

又过一周，澄光 **「答的是旧版」** 工单从 **每周两张** 降到 **零**。王姐再上传制度时，会等后台状态从 **「索引中」** 变 **「已生效」** 才发群通知；偶尔她会用 **「以普通员工预览问答」** 先问一遍哺乳假，看脚注版本号是不是 **2025.8**。

林薇给新同学讲 S6 第三课，把白板 **「知识从哪来」** 接成三行：

**「ACL 决定 **谁能看见**；Chunking 决定 **每一块是否完整**；版本与延迟决定 **员工看见的是不是 **今天该执行的那一页**。上传成功只是 **货车进厂**；**换架、下架旧纸、挂牌生效** 才是运营要盯的。」**

小陈把英文写在旁边：**Knowledge base versioning & update latency。** 李女士后来在回访里写：**「这次脚注写的是 8 月版，和人事窗口贴的通知一致——不像上个月，群里说新办法了，小言还在念旧纸。」**

林薇在季末白板 **「知识从哪来」** 第二格打了个勾——**哪一版算数、什么时候算数**，是 HR 敢把 **「去问小言」** 写进通知的前提；下一格她留了空：**「用户点脚注，能不能一眼信得过」**——那是 **引用展示** 的事。

## 概念正解

**知识库版本与更新延迟（Knowledge Base Versioning & Update Latency）** 指：在 RAG 知识库中，如何管理 **同一文档的多个修订版本**（哪一版 **当前生效**、旧版何时 **退出检索**），以及从 **运营上传** 到 **终端用户可检索到新内容** 之间的 **流水线时延** 与 **产品承诺**。它解决的是 **「后台明明更新了，员工问到的还是旧政策」**——常见根因不是模型幻觉，而是 **旧 chunk 仍在检索池**、**版本元数据缺失**、**上传成功被误认为已生效**、或 **索引同步尚未完成**。典型做法包括：**版本链（doc_id + version + 生效/失效日）**、**发布模式（立即 / 定时 / 草稿预览）**、**旧版废止与默认检索过滤**、**流水线状态可视化**、**脚注展示版本号**，以及可选的 **SLA 与更新中降级话术**。

回扣故事：李女士引用 **2025 版 §3.2**，是 **新版已入对象存储但旧 chunk 未废止**；王姐的 **绿色对勾** 只代表 **文件收到**；商小言价目表案是 **同类的跨应用版本延迟**；澄光 **替换即生效 + 进度状态 + 脚注版本号** 是中小可交付路径。

在 **S6 · 知识可运营、权限可审计** 中的位置：本篇锚定 **「知识从哪来」** 的第二层——**版本与生效**；承接 S6-02 **重切后如何切换**；为后续 **引用展示（Citation UX）**、**知识运营后台（谁上架/谁下架）** 打基础——脚注若连 **版本号都写不对**，运营无法审计。

在 **AI 产品岗** 的典型场景：

| 场景 | 具体例子 |
|------|----------|
| **需求文档** | 定义 **版本字段、生效模式、旧版处置、上传→可检索 SLA**；写清 **「上传成功」与「已生效」** 的 UI 差异 |
| **方案评审** | 问：**新旧并存多久？** 定时生效 **谁触发切换？** 失败重试 **会不会半套新旧？** 审计要不要 **保留废止块只读？** |
| **指标设计** | **版本陈旧引用率**（脚注指向已废止版）、**P95 索引延迟**、**上传→生效转化率**、**「更新中」降级触发次数** |
| **跨团队沟通** | 对运营：**「通知全员前先看 **已生效** 状态」**；对工程：**「废止要踢出默认检索池，不是只改展示」**；对客户成功：**「商家大促换价目，提前做 **定时生效 + 预览**」** |

## 类比锚定

**核心类比：图书馆换书——新书到了库房（上传），还要 **编目、上架、把旧版从外借架撤下**（切片索引 + 废止旧版），读者才能在架子上摸到 **当前版**；「书到了」≠「读者能借到」。**

| 你熟悉的 PM 经验 | 版本与延迟要素 |
|------------------|----------------|
| App **灰度发布 / 全量开关** | **定时生效、草稿预览、原子切换当前版指针** |
| 帮助中心 **文章 v3 替换 v2，旧链 301** | **doc_id 稳定 + version 递增 + 旧版 superseded** |
| 电商 **活动页定时上下线** | **effective_from / effective_to + 到点批任务切换** |
| CDN **缓存刷新要等 propagation** | **解析→切片→向量→索引的流水线延迟** |
| 合同 **「本版取代此前所有口头约定」** | **默认检索只命中当前生效版；脚注写版本号** |

## 类比边界说明

### A. 概念核心要点

1. **上传成功 ≠ 已生效**——产品必须把 **流水线阶段** 展示给运营，避免 HR「通知早了」。  
2. **版本是检索策略，不是文件名**——同一 `doc_id` 多版并存时，必须 **显式规则** 决定阿寻默认捞哪版。  
3. **废止旧版要踢出默认检索池**——仅在前台改展示、旧 chunk 仍可被 Rerank 命中，**脚注还会指向旧纸**。  
4. **延迟要可测、可承诺**——给出 **P95 索引时延** 或 **更新中话术**；大促/制度切换场景考虑 **定时生效**。  
5. **与 Chunking、ACL 串联**——改版常触发 **重切**；预览态、部门可见范围仍受 **ACL** 约束。

### B. 类比失效点

| 类比说法 | 失效点 | 更准确的理解 |
|----------|--------|--------------|
| 「像 Wiki 改一个字立刻全网可见」 | Wiki 多是 **单页覆盖**；RAG 是 **异步索引多副本**，还有 **向量与关键词双索引** | 要定义 **索引一致性与切换点** |
| 「旧版删掉就行」 | 合规常要求 **保留废止版只读** 供审计；粗暴删除 **脚注历史无法回放** | **退出默认检索** ≠ 物理删除 |
| 「延迟靠用户多刷几次」 | B 端 HR 背 **制度准确性**；员工不会替系统「刷索引」 | 用 **状态机 + SLA + 预览** 管理预期 |
| 「版本号写在文件名里就够了」 | 检索靠 **块元数据**；文件名未写入 chunk 时 **阿寻不知道哪版** | **版本字段必须进入索引与脚注契约** |

## 本集 Checklist

**标准 / 规范流程**

- [ ] 每文档 **版本链**（`doc_id` + `version` + 生效/失效日）；支持 **立即 / 定时 / 草稿预览**  
- [ ] 新版生效时 **旧 chunk 标废止并退出默认检索**；审计保留 **只读历史**（按需）  
- [ ] 运营后台 **流水线状态**（已上传 / 处理中 / 已生效 / 失败）与 **重试**  
- [ ] 书面 **SLA**（如制度类 P95 索引延迟）；未生效时 **降级话术** 可配置  
- [ ] 指标：**版本陈旧引用率**、**上传→生效 P95**；工单可 **按 doc_id 追溯**  
- [ ] 脚注契约含 **文档名 + 版本号 + 生效日**（与下篇 Citation UX 对齐）

**中小常用方案**

- [ ] **替换即生效**：同 `doc_id` 新版处理成功后 **自动废止上一版**  
- [ ] 上传页 **预计生效时间** + **「生效中请勿全员通知」** 提示  
- [ ] **单文档强制刷新索引** 止血；预览 **「以某角色试问答」**  
- [ ] 脚注至少展示 **版本号**，方便 HR 肉眼核对  

**何时升级到完整版**

- 客户要求 **定时生效、审批流、多版本并存对比**；**跨部门分批生效**；**监管审计** 需完整版本回放；或 **大促/制度切换** 频繁出现 **「通知已发、检索仍旧」** 类 P1 工单。
