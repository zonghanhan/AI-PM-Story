### 场景白板（读故事前 30 秒）

- **本集入口**：**应用 A｜商小言**——星尘卖给 **电商商家（租户）** 的智能客服；**周老板** 是某家居试点商家管理员；**小敏** 是商家客服坐席，在后台用 **AI 小言** 答买家问价。
- **多租户隔离（Tenant Isolation）**：白话：**商家 A 的知识、会话、配置、账单，绝不能被商家 B 读到或混用**——从数据库行、向量索引、缓存键到日志，**每条链路都要带租户钥匙**。
- **tenant_id**：租户唯一标识；检索、写入、缓存、计费 **默认必带**，漏一处就可能 **跨店串货**。
- **本集冲突**：木语工坊 **从没上传过某份底价话术**，小言回答买家时 **脚注却闪过别家字样**——疑似 **跨租户串库**。

## 寓言故事

### 一、脚注里闪过一行「别家的话」

澄光内小言运营台刚稳两天，**商小言** 侧却先炸了。

周老板是星尘 **家居类目试点** 的第十三家租户，店名叫「木语工坊」。小敏周三下午在商小言后台接待买家，问：**「这款橡木餐桌最低能给多少？能不能再送一套餐椅护垫？」**

**AI 小言** 答得礼貌，末尾照例挂了脚注 [1]。小敏扫了一眼正文，正要复制发送，脚注预览卡片 **突然多闪了一行小字**——像加载错位，半秒后消失：

> **来源 [1] 片段预览**：「……底价 **不得低于挂牌价七折**；对 **VIP 老客** 可额外申请 **两个点** 让利空间……」

小敏愣住。木语工坊 **从来没有「七折底价」「两个点让利」** 这套说法——他们合同里写的是 **「底价不低于八五折，赠品另议」**。更关键的是：周老板在开通商小言时 **明确勾选过「不上传内部底价表，仅上传对外 FAQ 与价目」**；后台知识库里 **搜不到任何含「底价」的文件名**。

她没敢把这段话发给买家，先截了 **动图录屏**（脚注闪错那 0.8 秒），在商家运营群里 @ 周老板：**「小言是不是串了别家的价？」**

周老板直接打了星尘 **真人支持** 电话。坐席按流程建工单，标题：**「疑似 **跨租户知识泄露**：脚注闪现非本店话术；租户 `tenant_muyu`，P1 候选，请产研初判。」** 工单附件是小敏的录屏和 **当次会话 ID**。

林薇收到转单，第一反应不是骂模型：**「先别写进对外公告说幻觉。周老板 **没传底价表却出现底价话术**——要么 **缓存/索引串租户**，要么 **共享语料没洗干净**。请小陈拉 **检索日志 + chunk 元数据**，看 [1] 的 `doc_id` 和 `tenant_id`。」**

---

### 二、不是胡说，是捞错了货架

小陈十分钟后在内部频道回：**「复现了，概率低但致命。模型没瞎编——**某一刻阿寻确实返回了别家 chunk**，Grounding 把片段塞进脚注预览；下一帧 rerank 或 ACL 二次过滤把它踢掉，**正文已改成木语对外 FAQ**，但 **脚注卡片缓存了上一跳的预览文本**。」**

他把当次链路摊成表：

```text
买家问题 → 商小言会话（tenant_muyu）
   ↓
向量检索（collection: rag_prod_v3）  ← 此处 filter 漏写 tenant_id
   ↓
Top 8 含 tenant_homeplus 的「内部底价指引」chunk（相似度 0.82）
   ↓
Rerank + 二次 filter（带 tenant_muyu）→ 该 chunk 被剔除
   ↓
生成正文：引用木语对外价目 ✓
   ↓
脚注 UI：预览层仍读了「上一跳候选集」里第一条的 snippet ✗
```

**「所以买家若手快截图，能看见 **隔壁『家加优品』** 的底价政策。」** 林薇在工单里写：**「属 **多租户隔离失效 + 引用 UI 未与最终上下文对齐** 叠加；非周老板误传文件。初判 **P1——商业机密类，影响范围待扫日志**。」**

她顺手拉了对照：**应用 C｜内小言** 去年做过 **租户级 collection 拆分**（澄光 `tenant_cg` 与星尘狗食 `tenant_stardust` 分库）；**商小言早期为了省成本**，多家中小商家 **共用一个向量 collection**，只靠 **查询时 metadata filter** 区分——这次 filter 在 **一次灰度重构里漏了一处**。

周老板在电话那头问：**「你们不是说 **租户隔离** 吗？我怎么知道以前还泄露过没有？」**

林薇只能如实：**「日志能查 **是否发生过 cross-tenant hit**；我们先 **止血 + 全量扫 30 天**。」**

---

### 三、漏一把钥匙，整排货架都不保险

当天下午，林薇拉小陈、负责商小言的算法同学和老何（路由值班）开了 **隔离加固会**。小陈在白板上画 **「租户钥匙该插在哪」**：

| 层级 | 该带什么 | 漏了会怎样（本案或常见） |
|------|----------|--------------------------|
| **对象存储 / 文档库** | 路径或桶按 `tenant_id` 前缀 | A 商家运营误删 B 家 PDF |
| **向量索引** | **独立 collection** 或 **强制 filter** | 本案：检索先捞到 **家加优品** chunk |
| **切片元数据** | 每个 chunk 写入时烙 `tenant_id` | 重索引脚本串库 |
| **检索 API** | 查询 **默认 AND tenant_id**；无租户拒绝 | 灰度分支忘传参 |
| **Rerank / 二次过滤** | 与检索 **同一租户约束** | 正文纠正了，**候选集仍脏** |
| **会话与记忆** | `session` 绑定 `tenant_id` | 买家上下文记到别家 |
| **缓存（检索结果 / 脚注预览）** | cache key 含 `tenant_id` | 脚注闪 **别家 snippet** |
| **配置与 Prompt** | 商家剧本、工具权限按租户 | B 家客服调到 A 家退货政策 |
| **日志与计费** | 全链路 `tenant_id` 可追踪 | 无法审计 **串了几次** |

算法同学指着重灾区：**「**共享 collection + 只靠 filter** 在工程上能跑，但 **任何一条链路漏 filter 就是 P1**。澄光内小言用 **分 collection**，商小言试点为省运维 **走了共享——这次代价来了。」**

林薇问：**「用户级 ACL（S6-01）和租户隔离什么关系？」**

小陈：**「**租户隔离是外墙**——李女士和隔壁公司不能互看；**ACL 是内墙**——李女士和 HR 不能互看。外墙没砌好，内墙再细也没用。」**

老何补一句路由侧：**「模型路由、工具调用、Token 计费 **早就按 tenant 分账**；最丢人往往是 **阿寻这条老链路**——当年先上的，后来补丁叠补丁。」**

### 四、先堵洞，再砌墙

林薇把 **小敏录屏** 又播了一遍：**「脚注闪了别家底价——不是胡说，是 **捞错货架**。」**

小陈：**「热修三件事：**补 tenant filter**、**脚注只渲染 final_context**、**缓存键必带 tenant_id**。」**

林薇问：**「用户级 ACL 和租户隔离什么关系？」**

小陈：**「**外墙**——木语和家加不能互看；**内墙**——李女士和 HR 不能互看。外墙没砌好，内墙再细也没用。」**

老何补：**「路由、计费早按 tenant 分账；丢人往往是 **阿寻老链路**——当年先上，补丁叠补丁。」**

大刘：**「共享 collection + filter 能跑，但 **漏一处 filter 就是 P1**。试点商家愿付企业版，**优先独立 collection**。」**

会上定 **24 小时止血** + **季度加固**，白板只写 **人话**：

| 会上定的 | 白话 |
|----------|------|
| **无 tenant_id 直接 400** | 默认拒绝（Deny by Default） |
| **三处强制 filter** | 向量/关键词/Rerank 统一封装 |
| **脚注只信最终上下文** | 不读中间脏候选 |
| **金丝雀探测** | 各租户独有 probe 句，不应命中他户 |
| **日志能答周老板** | 「过去 N 天是否串库」可报表 |

当晚小陈热修上线；商小言运营给周老板回电：**「已止血；30 天扫描 **另一起类似命中**，无大规模扩散证据。」**

### 五、接近结尾：外墙没砌好，内墙再细也白搭

周五，小敏重新试了十轮问价——脚注稳定指向 **木语对外价目 FAQ**，再没闪过 **「七折底价」**。周老板要了一份 **《跨租户访问扫描报告》** 才肯在试点续约书上签字。

林薇给新同学讲 S6 第六课，把季末白板 **「谁能看见」** 往外扩了一格：

**「S6-01 是 **同一公司里** 李女士能不能看 HR 页；今天是 **木语和家加能不能互看**。租户隔离不是 **注册时勾个 checkbox** 就结束——**每一条读库、每一次检索、每一个缓存键、每一张脚注卡片** 都要默认问：**这是谁家的货？** 漏一处，Grounding 越准，**泄露越像「官方背书」**。」**

她在白板 **「坏了怎么发现」** 那一行旁边画了个问号——**「周老板问 **以前漏过没有**，我们靠 **日志与金丝雀** 答；若日志本身没记 `tenant_id`，就连 **诚实回答** 都做不到。」** 下一篇，该讲 **检索与引用怎么留痕、怎么告警**。

小陈把英文写在旁边：**Multi-tenant Isolation Hardening.** 林薇补中文：**多租户隔离再加固——**不是重做 SaaS 多租户，是给 **RAG 这条后加的长尾链路** 补课。**

## 概念正解

**多租户隔离再加固（Multi-tenant Isolation Hardening）** 指在已有「账号分租户」前提下，对 **知识库、向量检索、缓存、会话、配置、日志、引用 UI** 等 **全链路** 再次审查与加固，确保 **租户 A 的数据与推理上下文绝不会进入租户 B**——尤其在 **共享向量索引、灰度重构、缓存复用** 时。它解决 **「商家从没上传某文件，AI 却引用别家内容」** 类事故：根因常是 **检索 filter 遗漏、缓存键未含 tenant、脚注展示中间候选、批量索引脚本串库、测试数据污染生产**，而非模型幻觉。核心手段：**分域存储（独立 collection / 桶前缀）、查询默认 deny、写入元数据烙 tenant、缓存与 UI 与最终上下文对齐、跨租户金丝雀探测、可审计日志**。

回扣故事：小敏看到脚注 **闪过家加优品的底价话术**——检索曾 **无 tenant filter 捞到隔壁 chunk**，Rerank 虽剔除，**脚注预览仍读了脏候选**；木语 **未上传底价表** 反而成为 **铁证**；止血靠 **补 filter + 脚注对齐最终上下文 + 金丝雀扫描**。

在 **S6 · 知识可运营、权限可审计** 中的位置：S6-01 管 **租户内授权**；本篇管 **租户间外墙**——**「谁能看见」** 要先保证 **「看见的都是自己家的」**；为 **「坏了怎么发现」**（检索可观测性）铺垫。

在 **AI 产品岗** 的典型场景：

| 场景 | 具体例子 |
|------|----------|
| **需求文档** | 写清 **每层级隔离策略**（存储 / 索引 / 检索 / 缓存 / UI）；**共享 vs 分库** 选型与 **升级触发条件** |
| **方案评审** | 问：**灰度分支是否共用检索入口？** 脚注数据来自 **最终 prompt 还是中间候选？** 无 `tenant_id` 请求 **默认拒绝还是默认全库？** |
| **指标设计** | **cross-tenant hit 次数**、**金丝雀失败率**、**隔离类 P1 工单**、**分库迁移进度** |
| **跨团队沟通** | 对商家：**「隔离是链路工程，不是一句承诺」**；对研发：**「filter 封装一处，禁止复制粘贴」**；对法务：**「日志保留多久能举证 **未泄露 / 泄露范围**」** |

## 类比锚定

**核心类比：连锁商场 **统一收银系统**——每家门店（租户）货品、价签、小票模板分开；若仓库 **共用一个条码池** 但收银扫码 **偶尔不校验门店号**，就会把 **A 店库存** 当成 **B 店** 卖出。RAG 的向量库是 **共享仓库**，`tenant_id` 是 **门店号**，检索 filter 是 **扫码校验**。**

| 你熟悉的 PM 经验 | 多租户隔离再加固 |
|------------------|------------------|
| SaaS **org_id / tenant_id** 行级数据隔离 | 文档、chunk、会话 **元数据必带 tenant** |
| **分库分表** vs **单库 + 字段过滤** | **独立向量 collection** vs **共享池 + 强制 filter** |
| CDN / Redis **缓存 key 带租户** | 检索结果、Embedding、脚注 **缓存键含 tenant** |
| **预发环境数据** 不能进生产 | 索引脚本、测试商家 **禁止写入生产 collection** |
| 支付 **对账按商户号** 扫错账 | 日志 **按 tenant 审计 cross-hit** |
| 收银小票 **只打印本店成交明细** | 脚注 **只展示进入最终上下文的来源** |

## 类比边界说明

### A. 概念核心要点

1. **租户隔离是链路属性，不是合同文案**——注册分租户后，**每条读路径仍要验 tenant**。  
2. **共享索引省成本，但放大漏 filter 后果**——中小可共享，须 **封装统一 filter + 金丝雀 + 分库升级路径**。  
3. **Rerank 剔除 ≠ 用户没看见**——**脚注、预览、日志、缓存** 可能已暴露 **中间候选**。  
4. **与 ACL 分层**：**外墙（租户）** 先于 **内墙（用户/角色）**；内墙不能替代外墙。  
5. **可审计才能对客户诚实**——无 `tenant_id` 日志，**无法回答「以前漏过没有」**。

### B. 类比失效点

| 类比说法 | 失效点 | 更准确的理解 |
|----------|--------|--------------|
| 「和数据库多租户一模一样」 | 向量检索 **近似匹配** 可能 **高相似误捞**；UI 有 **中间状态** | 要 **检索 + 展示 + 缓存** 三层对齐，不只 DB 行权限 |
| 「每租户独立部署最省心」 | 成本与运维 **指数上升**；平台能力 **无法复用** | **逻辑强隔离 + 物理分域按需升级**，不是一刀切单机 |
| 「filter 写上就万无一失」 | 灰度、脚本、**异步重索引** 仍可能 **漏带参** | **默认拒绝 + CI 回归 + 金丝雀** 组合治理 |
| 「串租户只是小概率，可以靠客服道歉」 | B2B **底价/合同/制度** 泄露 **直接违约与竞业风险** | 按 **P1 数据事件** 设计 playbook，不是体验 bug |
