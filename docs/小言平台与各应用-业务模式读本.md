# 小言平台与各应用：业务模式读本

> **读者**：没接触过 B 端 AI SaaS、多租户、多产品线的读者；转行 PM、售前、实施、客服运营均可。  
> **与寓言的关系**：本仓库正文在 `stories/`；本文是 **非故事、可查阅的架构说明**，与 [系列世界观与阅读指南](../stories/世界观.md) 一致，但更侧重 **商业运作、角色与真实业界对照**。  
> **虚构设定**：公司名 **星尘智能**、产品名 **商小言 / 修小言 / 内小言 / 账小言** 为系列统一命名；对照现实时可直接换成「某智能客服 SaaS」「某设备售后 App」「某飞书机器人」。

## 1. 先用一张图建立直觉

```text
                         ┌─────────────────────────────────┐
                         │  星尘智能（软件厂商 / Vendor）     │
                         │  收钱对象：企业客户（租户）        │
                         │  不卖账号给：淘宝买家、路人 C 端   │
                         └─────────────────────────────────┘
                                            │
                    签约 · 开通 tenant_id · 数据隔离
                                            │
         ┌──────────────┬──────────────┬──────────────┬──────────────┐
         ▼              ▼              ▼              ▼              │
    应用 A 商小言   应用 B 修小言   应用 C 内小言   应用 D 账小言      │
    电商商家租户    设备客户租户    企业飞书租户    常与 B 同租户      │
         │              │              │              │              │
    商家客服为主    工程师为主      员工为主        财务接口人         │
    间接服务买家    查手册报修      问制度年假      对账入账 API       │
         │              │              │              │              │
         └──────────────┴──────────────┴──────────────┴──────────────┘
                                            │
                         共用：小言平台（检索、路由、护栏、计费、评测…）
```

**三个词先记牢**：

| 词 | 含义 | 例子 |
|----|------|------|
| **厂商（Vendor）** | 做软件、收订阅费的公司 | 星尘智能 |
| **租户（Tenant）** | 签约的一家客户组织，`tenant_id` 隔离数据 | 木语工坊、澄光制造 |
| **终端用户（End User）** | 在租户账号下 **实际使用产品** 的人 | 商家客服小敏、工程师张先生 |

**买家、星尘产研、阿梅（星尘售后运营）** 一般 **不是** 商小言/修小言的「租户终端用户」——角色不同，下文会反复出现。

## 2. 为什么看起来「复杂」？其实是两层叠加

很多读者晕，是因为把两件事叠在一起看了：

1. **一个厂商做了多条产品线**（A/B/C/D 四个应用）  
2. **每条产品线又是多租户 SaaS**（很多商家/很多工厂，数据不能串）

现实中：

- 只做 **一个应用 + 一个租户**（大商家自建客服）→ 结构简单  
- 星尘要做 **一个平台卖多家客户、多条场景** → 必须出现 **平台层 + 租户隔离 + 多应用**

**简化口诀**：

```text
先问：这是哪一个应用？（A/B/C/D）
再问：这是哪一个租户？（tenant_id）
最后问：终端用户是谁？（客服 / 工程师 / 员工 / 财务）
```

## 3. 小言平台层（四个应用共用）

平台 **不单独卖给最终用户**，而是四个应用的 **底座**。

| 能力（故事昵称） | 做什么 | 现实对应 |
|------------------|--------|----------|
| **阿寻** | 检索 / RAG 知识库 | 向量库 + 文档解析 + 混合检索 |
| **老何** | 模型路由（一至四楼） | 按场景选便宜/贵模型、升级人工 |
| **老关** | 安全护栏 | 输入输出审核、敏感词、工具动作拦截 |
| **统一网关** | 流式、Token 计费、评测 | API 网关、可观测、成本台账 |

**商业模式（平台侧）**：

- 收入：各应用 **订阅费 + 用量（Token/API 调用）+ 企业版增购**  
- 成本：模型 API、向量存储、运维、**厂商自己的真人支持**（可选 SLA 包）  
- 星尘内部角色：林薇（PM）、小陈/大刘（研发）、阿梅（对客户交付与运营）、苏姐（星尘自身财务与计费）

| 维度 | **A 商小言** | **B 修小言** | **C 内小言** | **D 账小言** |

## 5. 应用 A：商小言

### 5.1 业务运作模式

```text
星尘 ──SaaS 签约──► 电商商家（租户）
                      ├─ 运营上传：价目、合同、FAQ、退货政策
                      ├─ 客服登录商小言：查条款、办退货、生成答复依据
                      └─ 店铺渠道 ──► 买家咨询（旺旺/企微/自营商城客服窗）
```

**两条触达买家的路**（常并存，不是二选一）：

| 路径 | 谁操作商小言 | 买家感受 |
|------|--------------|----------|
| **客服副驾驶** | 客服查完再回复 | 像在跟「店家客服」聊天 |
| **店铺智能客服窗** | 买家在店里直接聊，背后接商小言 | 仍以为在跟店说话，**不注册星尘账号** |

系列早期故事（第 3–5、7、11 篇）以 **客服查合同、办退货** 为主；**买家直连全自动** 在队列 **S9 用户端语音下单** 中再展开。

### 5.2 商业模式

| 项目 | 说明 |
|------|------|
| **谁付钱** | 电商商家（租户） |
| **计费常见项** | 坐席数 / 会话量 / Token 用量 / 企业版（多店铺、审计、独立索引） |
| **谁担责** | 答错退货政策、乱承诺折扣 → **商家对买家负责**；星尘对商家有 B 端 SLA |
| **增值** | 对接商家 ERP/订单系统、多租户运营台、投毒防护、可观测报表 |

### 5.3 产品目标

- **S1 季**：依据 **商家自己的知识库** 答合同/价目/退货，**有出处、少幻觉**  
- **S6 季**：知识可运营、**租户间不串库**、引用敢点、越权导出可防  
- **远期 S9**：买家侧语音下单/报修式交互（仍挂在 **商家租户** 下）

### 5.4 适用客户

| 更适合 | 不太适合 |
|--------|----------|
| 多 SKU、政策文档多、客服重复查条款的 **电商/品牌商家** | 几乎没有文档、全靠口头报价的小摊 |
| 已在淘宝/拼多多/自营商城有客服团队，想 **提效查资料** | 希望 **零客服、100% 全自动对 C 端** 且不愿承担资损风险 |
| 需要 **多店铺/多品牌** 统一知识运营的中大型商家 | 仅偶尔用 ChatGPT 复制粘贴的个人店 |

### 5.5 角色人群

| 角色 | 是否租户 | 是否登录商小言 | 典型诉求 |
|------|----------|----------------|----------|
| 星尘产研/阿梅 | 否 | 否（平台后台） | 迭代产品、处理商家工单 |
| 商家老板/运营 | 是（管理员） | 是 | 买系统、管知识库、看报表 |
| 商家客服 | 租户内员工 | **主用户** | 查合同第几条、办退货、答 FAQ |
| 买家 | 否 | **否**（只聊天） | 能退吗、几天发货、最低价多少 |
| 星尘真人支持 | 否 | 否（厂商 SLA） | 租户级故障、接管异常 run（S7 后） |

### 5.6 买家直连时的业务模式

「买家直连」指：买家在 **店铺客服窗 / 自营商城 IM** 里直接和机器人对话，**不必等商家客服先打开商小言后台**。这与 **客服副驾驶**（客服查完再回）是 **两种并行产品形态**，计费与风险模型不同。

#### 5.6.1 两条路径对照

| 维度 | **客服副驾驶** | **买家直连（店铺窗）** |
|------|----------------|------------------------|
| **谁登录商小言** | 商家客服坐席 | **通常无人登录**；买家只在店铺渠道里聊 |
| **商小言界面** | 客服工作台、Copilot 侧栏 | **Widget / 店铺 IM 机器人**（可嵌淘宝、企微、自营 H5） |
| **典型问题** | 「合同第几条」「这单怎么退」——客服内部查 | 「能退吗」「我的单到哪了」——买家直接问 |
| **订单/写操作** | 客服确认后代办（第 4 篇 Agent 退货） | 买家发订单号 → 小言调 `get_order` 等工具；**高风险要确认/转人工** |
| **系列正文** | 第 3–5、7、11 篇主场景 | 第 4 篇有买家发单号办退；**S9 预告** 买家语音下单专篇 |
| **买家是否星尘用户** | 否 | **否**（仍是商家的顾客，不是星尘 SaaS 账号） |

```text
路径 A · 客服副驾驶
  买家 ──店铺 IM──► 商家客服小敏 ──商小言后台──► 查价目/合同/订单
                              └── 复制改写 ──► 回复买家

路径 B · 买家直连
  买家 ──店铺客服窗(widget)──► 商小言机器人（同一 tenant：木语）
         │                        ├─ 公开 FAQ → RAG（价目、退货政策）
         │                        ├─ 我的订单 → 订单 API（带买家身份）
         │                        └─ 搞不定 → 转商家人工客服（同 session 上下文）
         └── 不经过星尘 App 注册
```

#### 5.6.2 商业运作模式（谁签约、谁付钱、谁担责）

```text
星尘 ──SaaS──► 木语工坊（tenant_id: muyu）── 开通「店铺智能客服」能力
                    │
                    ├─ 商家付：订阅 + 会话量/Token + 可选订单接口实施费
                    ├─ 买家付：0（不对星尘付费）
                    └─ 对外品牌：永远是「木语客服」，不是「星尘小言」
```

| 项目 | 买家直连时怎么算 |
|------|------------------|
| **合同主体** | 星尘 ↔ **商家租户**；买家不在合同里 |
| **计费** | 常按 **C 端会话条数 / 机器人消息 Token** 计入 **租户账单**（木语付） |
| **责任链** | 机器人答错政策、乱承诺退款 → **商家对买家** 负责；星尘对商家 SLA |
| **增值档位** | 订单查询工具、身份验证、转人工队列、投毒防护（S6-08）、导出闸（S6-09） |
| **与坐席关系** | 直连 **减重复劳动**，不是取消客服；复杂单 **转人工**，人工仍可用副驾驶 |

**ROI 怎么讲给商家**：大宗 **FAQ 自动答** + 简单查单；客服从「打字查资料」变成 **处理纠纷与例外**——若直连后 **转人工率极高且坐席代下单**，说明自动化未交付，商家不会长期付费。

#### 5.6.3 买家直连时，订单怎么不串（四层闸）

买家直连最容易被问：**每个买家订单不同，会不会串？** 靠 **租户 + 会话 + 身份 + 工具鉴权**，不是靠「每个买家一个知识库」。

| 层级 | 防什么 | 怎么做 |
|------|--------|--------|
| **① 租户** | 木语买家看见家加价目 | 全链路 `tenant_id`（S6-06） |
| **② 会话** | 买家甲看见买家乙的聊天记录 | 每人一条 **`session_id`**，记忆不跨会话乱灌 |
| **③ 身份** | 未验证就查他人订单 | 店铺传入 **`buyer_id`**（已登录），或 **订单号 + 手机尾号/验证码** |
| **④ 工具** | 模型猜订单号、批量导出 | 订单 **只走 ERP API**，不进向量库；`get_order` **绑定会话主体**；禁止猜单（第 4 篇） |

```text
公开知识（人人一样）          私人数据（每人不同）
─────────────────────        ─────────────────────
价目、退货政策、材质 FAQ  →  RAG 检索
订单状态、地址、手机号      →  订单工具 API（验身后）
```

S6-09 在内小言讲 **`subject=self`（只查本人）**；搬到商小言即：**工具入参的买家 ID 必须与会话绑定身份一致**。木语周老板担心的「套出全店订单」属于 **工具越权（路径 B）**，与检索 ACL（路径 A）是 **两道闸**。

#### 5.6.4 常见产品分档（商家怎么开买家直连）

| 档位 | 自动处理 | 典型能力 | 风险 |
|------|----------|----------|------|
| **L0 仅 FAQ** | 包邮吗、材质、营业时间 | 只开 RAG，**不接订单工具** | 低 |
| **L1 登录买家查单** | 我的物流、能否退 | 店铺登录态传 `buyer_id` + `list_orders` | 中；要做好身份传递 |
| **L2 未登录验身查单** | 订单号 + 尾号查进度 | 短信/滑块验证后再调 API | 中；防撞库 |
| **L3 Agent 办事** | 自动发起退货、改地址 | 第 4 篇式多步 tool + **确认卡片** | 高；要审批/上限/转人工 |
| **L4 语音下单** | 说规格、确认下单 | **S9 队列**；ASR + 防误触 | 高 |

中小商家常见落地：**先 L0→L1**，再视客诉开 L3；**不要默认全开 L3**。

#### 5.6.5 与平台店铺渠道的关系

买家直连 **不意味着** 买家来星尘官网聊天，而是：

| 渠道 | 谁提供入口 | 商小言在哪 |
|------|------------|------------|
| **淘宝/拼多多客服** | 平台 IM | 通过 **平台开放接口 / 三方客服 SaaS** 接入 |
| **自营商城 / 小程序** | 商家 | **H5 widget** 或客服 SDK |
| **企微客服** | 商家 | 企微侧边栏或机器人 webhook |

星尘卖给木语的是 **能力与租户后台**；**买家动线仍停在店铺里**。对标：有赞/微盟里的「智能客服插件」——**插件背后是商小言，门面是店铺**。

#### 5.6.6 本系列对买家直连的覆盖与简化

| 话题 | 系列里有没有 | 在哪里 | 简化说明 |
|------|-------------|--------|----------|
| 买家不登录星尘 | 有 | `世界观.md` §4.1；本文 §5.1 | — |
| 店铺 widget 概念 | 有 | 世界观 Mermaid `客服会话 / -widget` | 未写各平台对接细节 |
| 买家发订单号 Agent 退货 | 有 | **第 4 篇** `get_order`、禁止猜单 | 主场景仍是 **商家侧办退**，非全自动 C 端 |
| 租户间不串 | 有 | **S6-06** 商小言主场景 | — |
| 工具越权 / 导出 | 有 | **S6-09** 对照商小言买家套地址 | 主故事是内小言 HR |
| `buyer_id` 登录态传参 | **未成篇** | 读本归纳 | 真实项目必备，寓言未专写 |
| 买家语音下单 | **队列 S9** | `世界观.md` §3.1 | 尚未落稿 |

**为何早期寓言偏客服副驾驶**：B 端付费、答错合同 **先在内网查准** 再对外，风险小于机器人直接对 C 端承诺退款。读者可把 **第 4 篇 + S6-06/09 + 本节** 拼成买家直连的完整图；**S9** 负责把 C 端交互讲透。

## 6. 应用 B：修小言

### 6.1 业务运作模式

```text
星尘 ──企业版签约──► 设备客户企业（租户，如澄光制造）
                        ├─ 管理员：导入设备手册、SOP、停产公告
                        ├─ 张先生等现场人员：App/微信 拍照报修、查滤芯、问质保
                        └─ 可选对接：客户 WMS、审批流、工单系统（S7 办事链）
```

与商小言的核心差异：**没有「店铺买家」这条 C 端链**；用户全是 **客户企业自己的员工**。星尘阿梅的角色是 **帮客户企业用好修小言**，不是澄光车间里的操作工。

### 6.2 商业模式

| 项目 | 说明 |
|------|------|
| **谁付钱** | 设备厂商的客户企业，或 **设备厂商打包进售后服务**（白标/联名） |
| **计费常见项** | 企业账号数、设备型号库容量、Agent 办事次数、对接实施费 |
| **增值** | 账小言模块、多步报修 Agent、审批闸、人工接管 SLA |
| **厂商支持** | 灰度期常见；成熟后 **自动办结率** 决定客户是否续费 |

### 6.3 产品目标

- **S3 季**：现场 **拍照能识别、能答手册、能报修**；平台有护栏、路由、流式  
- **S7 季**：从「演示一键成功」到 **值班**：run 可见、审批、重试、人工接管  
- **与商小言关系**：**并行售卖**，不同租户、不同知识库，**不共用同一 tenant**

### 6.4 适用客户

| 更适合 | 不太适合 |
|--------|----------|
| 卖工业设备/硬件、售后依赖 **手册 + 备件 + 工单** 的企业 | 纯软件、无现场维保团队 |
| 现场工程师多、希望 **少打电话问总部** | 不愿开放 WMS/工单 API 对接 |
| 客单价高、愿意为 **售后体验与审计** 付费 | 仅需一个静态 FAQ 页 |

### 6.5 角色人群

| 角色 | 典型人物 | 做什么 |
|------|----------|--------|
| 客户企业管理员 | 澄光 IT | 开账号、绑手册库、接 WMS |
| 现场工程师 | **张先生** | 拍照报修、查库存、看停产公告 |
| 审批人 | 老周 | 费用/换件审批（S7-02） |
| 仓库协同 | 小刘 | 认拣货单 PK 号（S7-03/04） |
| 星尘阿梅 | 厂商售后运营 | 看客户录屏、改产品、灰度 |

### 6.6 设备客户企业、设备厂商与常见业务模式

读修小言时最容易混的两个「厂」：**卖软件的是星尘**，**卖机器的是设备厂商**，**在车间里用的是设备客户企业**。下面单独拆开，并说明现实里还有哪些卖法，以及寓言为什么先写最简单的一种。

#### 6.6.1 三个主体对照

| 主体 | 是谁 | 和修小言的关系 | 系列里的例子 |
|------|------|----------------|--------------|
| **星尘智能** | **软件厂商**（产研运） | **研发** 修小言、卖平台能力 | 林薇、小陈、阿梅 |
| **设备厂商** | **卖工业/硬件设备** 的公司（可选角色） | 可能 **自研/贴牌/OEM 渠道** 售后软件；对外常做 **官方售后** | 故事少点名；第 17 篇写「设备厂商/工业品客户」 |
| **设备客户企业** | **买了设备并在自己现场使用、维保的组织** | 系列默认的 **租户（tenant）** | **澄光制造** |

**设备客户企业** = 相对星尘而言的 **B 端签约客户**，不是 C 端个人。典型包括：

- **制造工厂**（如澄光）：自有产线，买了注塑机、冷却塔，自己保养报修  
- **运维/维保外包方**：承包某园区设备运维，工程师驻场  
- **集团下属工厂**：同一集团内一个法人主体对应一个 tenant（也可再分子公司）

**不是**设备客户企业的典型情况（除非故事特别声明）：

- 星尘自己（星尘是软件厂，不是修小言租户里的「工厂」）  
- 木语工坊那种 **电商商家**（那是商小言租户）  
- 仅 **买软件做集成** 的系统集成商——若未展开，系列不当作主用户

**设备厂商** = 把 CF-220、滤芯、整机 **卖给澄光** 的那类 **设备生产企业或品牌方**。它通常：

- 提供 **质保、备件、官方热线、现场派工**  
- 持有 **机型手册、停产公告、配件目录** 的 **权威版本**  
- **可能** 自己做售后 App，也可能只卖机器、售后由客户自理  

在系列里，设备厂商 **很少作为具名角色出场**，因为默认叙事是 **星尘 → 澄光** 直客；但现实世界大量项目是 **星尘 → 设备厂 → 多家工厂** 或 **设备厂自研**。

#### 6.6.2 常见业务模式（四种）

```text
模式 1 · 直客 SaaS（系列默认）
  星尘 ──企业版──► 设备客户企业（澄光）──► 张先生用「修小言」

模式 2 · 设备厂商白标 / 打包
  星尘 ──OEM/白标──► 设备厂商 ──► 澄光等客户工厂
  张先生看到「XX 设备服务助手」，底层可能是修小言

模式 3 · 设备厂商自研
  设备厂商 IT 自研售后 App / 大模型客服
  星尘不参与；产品机制仍可类比（RAG、Agent、run）

模式 4 · 双层售后（故事未专篇）
  澄光自建维保（模式 1）+ 疑难问题仍打设备厂 400
  软件可能两套：本厂 WMS 工单 + 设备厂远程诊断入口
```

| 模式 | 谁付钱 | 租户通常归谁 | 手册/备件库谁维护 | 对接工单/WMS |
|------|--------|--------------|-------------------|--------------|
| **1 直客** | 澄光 | **澄光** `tenant_id` | 澄光上传 + 设备厂 PDF | **澄光** WMS/审批（S7） |
| **2 白标** | 设备厂或澄光 | **设备厂大租户** 或 **一厂一 tenant** | 设备厂统一机型库，工厂侧本地规则 | 常要 **双系统**：厂级 + 客户级 |
| **3 自研** | 设备厂 | 设备厂平台 | 设备厂 | 设备厂 ERP |
| **4 双层** | 分开谈 | 澄光 tenant + 设备厂服务台 | 两边各一份 | 澄光本地为主 |

第 13 篇《抽屉里的口音片》里的 **多租户白标** 机制（不同租户不同称谓/LoRA），在修小言侧可对应 **模式 2**：设备厂把「修小言」包装成自家品牌，澄光员工无感。

#### 6.6.3 本系列做了什么简化、为什么

| 简化点 | 系列怎么写 | 现实更复杂处 | 为何先简化 |
|--------|------------|--------------|------------|
| **只画一条卖法** | 星尘直签 **澄光**（模式 1） | 设备厂渠道、白标、子租户 | 一个 `tenant`、一个张工，**教机制时不分心** |
| **设备厂商不具名** | 手册似澄光自有库 | 手册版权常在 **设备厂**，需同步/授权 | 聚焦 **RAG/Agent/run**，不先开 IP 与渠道合同课 |
| **售后全在客户企业内部** | 报修、WMS、审批、老周都在澄光 | 疑难件要 **设备厂派工**、质保判定在厂方 | S7 办事链绑 **客户 WMS**，一条链讲清即可 |
| **张先生 = 终端用户** | 澄光工程师 | 也可能是 **设备厂驻场工程师** 服务多家客户 | 用户画像统一为「现场工程师」 |
| **星尘 = 唯一软件研发方** | 林薇产品线 | 模式 3 下研发方是设备厂 | 与全系列「星尘小言平台」叙事一致 |
| **账小言同 tenant** | 澄光内对账 + 报修 | 设备厂与工厂结算可能另有一套 | 减少法人主体，**D 与 B 共用租户** 好讲 |

**读者若做真实方案**，应在模式 1 的基础上自问：

1. 机型手册是 **客户上传** 还是 **设备厂推送**？  
2. 工单落在 **客户 WMS** 还是 **设备厂服务云**？  
3. `tenant_id` 是 **一家工厂** 还是 **设备厂平台下的子组织**？  

系列 **没有写错**，是 **故意只教一层**；等读者掌握 S3/S7 的 RAG、办事链、人工接管后，再把上表 **模式 2～4** 叠回去即可。

#### 6.6.4 与商小言的渠道类比（帮助记忆）

| | 商小言 | 修小言 |
|--|--------|--------|
| 系列默认租户 | 电商商家（木语） | 设备客户企业（澄光） |
| 常见渠道形态 | 有赞/微盟 **内置** 智能客服 | 设备厂 **打包** 售后 App |
| 终端用户 | 商家客服（+ 间接服务买家） | 现场工程师 |
| 白标 | 商家品牌客服窗 | 「XX 官方维保助手」 |

## 7. 应用 C：内小言

### 7.1 业务运作模式

```text
星尘 ──按企业部署──► 某一飞书/钉钉组织（租户）
                      ├─ HR/法务上传：制度、年假、福利 PDF
                      ├─ 员工在 IM 里 @ 内小言：问「我们公司」政策
                      └─ 权限：谁能看见 HR 专区（S6 ACL）
```

**狗食（自研自用）** 与 **对外售卖** 可同时存在：星尘可以是租户 T1，澄光可以是租户 T2——**两个 tenant，两套制度库，不能串**。

### 7.2 商业模式

| 项目 | 说明 |
|------|------|
| **谁付钱** | 采购企业 IT / HR / 数字化部门 |
| **计费常见项** | 员工数、文档量、高级权限与审计、混合检索 |
| **卖点** | 减少 HR 重复答疑、制度 **有脚注可核对**、上架可运营（S6） |
| **合规** | 检索 ACL、废止版本、投毒防护——政企 HR 场景敏感 |

### 7.3 产品目标

- **S4 季**：跨天 **记得住且不串人/串库**（Memory + Hybrid Retrieval）  
- **S6 季**：**知识从哪来、谁能看见、坏了怎么发现**——运营台 + 权限 + 可观测  
- **与商小言**：共用平台能力，**不同租户、不同应用入口**，故事里的「李女士」是 C 的典型用户，不是商家客服

### 7.4 适用客户

| 更适合 | 不太适合 |
|--------|----------|
| 制度文档多、HR 被反复问年假/报销的 **中大型企业** | 十几人团队、制度口头传达即可 |
| 已用飞书/钉钉，希望 **机器人嵌在 IM** | 不愿整理 PDF、不接受上架流程 |
| 需要 **部门级权限**（工艺部看不见 HR 内部指引） | 只要公网 ChatGPT 随便问 |

### 7.5 角色人群

| 角色 | 典型人物 | 说明 |
|------|----------|------|
| 企业员工 | **李女士** | 问年假、育儿假；脚注对制度 |
| HR/知识运营 | 王姐（澄光） | 上传制度、发布、预览 |
| 法务 | 李法务 | 批准发布、审下架 |
| 星尘员工 | 林薇等 | 仅当星尘 **自己也是租户** 时才是内小言用户 |

## 8. 应用 D：账小言

### 8.1 业务运作模式

```text
客户企业（常与修小言同 tenant）
  ├─ 接口人（张先生/周会计）：发起对账、确认结构化结果
  ├─ 账小言：汇总 MES/PLC 等数据 → 生成符合 ERP 的 JSON
  └─ 客户 ERP：import 入账（写操作需人确认）

星尘侧
  ├─ 苏姐：星尘自身计费、成本、厂商财务规则
  └─ 财务中台 API：与账小言模块对接（不是客户工厂财务）
```

**关键**：账小言 **不是**「聊天很开心」的产品，核心是 **字段契约 + 结构化输出 + 多步状态**（与第 21 篇、S7 办事链衔接）。

### 8.2 商业模式

| 项目 | 说明 |
|------|------|
| **谁付钱** | 修小言 **企业版 / 大客户增购** |
| **计费** | 对接实施、按账期/行数、API 调用 |
| **价值** | 减少手工 Excel 对账、**半张表进不了 ERP** 的集成成本 |
| **边界** | 坐席 **可查不可替客户财务点确认入账**（S7-04） |

### 8.3 产品目标

- 对账结果 **可结构化导入** 客户 ERP  
- 多数据源（MES vs PLC）差异 **可解释、可审计**  
- 与修小言 **同一租户上下文**，但 **权限比聊天更严**

### 8.4 适用客户

- 已有修小言或类似售后系统、存在 **业财对账 / 结算** 痛点的设备客户  
- 有 ERP 接口能力或愿意做集成项目的中大型企业  

### 8.5 角色人群

| 角色 | 做什么 |
|------|--------|
| 客户财务/计划接口人 | 确认入账、处理差异 |
| 张先生 | 对账场景下的业务侧确认人 |
| 苏姐 | **星尘内部**，管模型成本与厂商账单，不是客户对账员 |

```text
                    ┌─────────────────┐
                    │   星尘商务合同   │
                    └────────┬────────┘
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
   单买商小言           单买修小言          单买内小言
```

| 星尘阿梅/CS | 上线培训、灰度、事故协同 |
| 星尘研发 | 平台能力、租户隔离、SLA |

## 10. 同类产品还可能长什么样？（简化理解）

星尘的 **「平台 + 多应用 + 多租户」** 不是唯一形态。用下面几种模式对照，更容易理解「什么时候简单、什么时候复杂」。

### 10.1 模式对照表

| 模式 | 谁建 | 谁用 | 结构复杂度 | 现实例子 |
|------|------|------|------------|----------|
| **① 星尘式多租户 SaaS** | 星尘 | 很多商家/工厂各一个 tenant | 高 | 智齿、网易七鱼、某大模型客服云 |
| **② 大商家自建单租户** | 商家自己的技术团队 | 仅本品牌买家/客服 | **低** | 头部电商自建 AI 客服 + 自营商城 |
| **③ 垂直 SaaS 内置 AI** | 商城 SaaS 厂商 | 店家用、买家用 | 中 | 有赞/微盟店铺智能客服插件 |
| **④ 企业内网 Copilot** | 集团 IT 或星尘内小言 | 仅员工 | 中 | 飞书智能伙伴、钉钉 AI 助理 |
| **⑤ 纯 API / 集成商** | 客户 SI 集成 | 嵌入客户原有系统 | 中偏高 | 只买 OpenAI + 自研 RAG，无品牌前台 |

### 10.2 你举的例子：大商家自建 AI 客服（模式 ②）

```text
某头部家具品牌（只有一家店，不做 SaaS 厂商）
  ├─ 自研或使用开源：RAG + 大模型 API
  ├─ 知识库：自家价目、合同（只有一个 tenant， mentally 就是「我自己」）
  ├─ 商城客服窗：买家直接聊
  └─ 没有：tenant_id、跨商家隔离、星尘阿梅、多应用 A/B/C/D
```

**为什么更简单**：

- **一个组织、一套数据、一个商城** → 不需要多租户  
- **买家直连** 可以默认，因为 **品牌自己对 C 端负责**，没有「帮别的商家托管」问题  
- **没有修小言/内小言/账小言** → 没有多产品线叙事  

**代价**：

- 自建团队、模型选型、评测、运维自己扛  
- 要做 ERP/WMS 对接仍会出现 **S7 式办事链复杂度**——那是 **业务集成深度**，不是 SaaS 多租户带来的  

### 10.3 什么时候星尘式架构「值得」？

| 条件 | 说明 |
|------|------|
| **客户多家** | 服务成百上千商家/工厂，必须 `tenant_id` 隔离 |
| **多条产品线** | 同一研发底座卖客服、售后、内问、对账 |
| **统一计费与合规** | Token、审计、红队、发布门禁一次建设多应用复用 |
| **厂商运营** | 需要阿梅类角色做跨客户灰度与 SLA |

### 10.4 三条简化问题（遇到任何「小言」类产品都适用）

1. **这是给谁用的？** B 端员工 / C 端买家 / 财务接口  
2. **知识库归谁？** 一个组织还是多组织隔离  
3. **写操作谁批准？** 纯问答 / 客服代发 / 系统 API 入账  

答完这三问，再决定要不要 **租户、审批闸、人工接管**——很多「复杂」是第 3 问带来的，不是 AI 聊天本身。

## 11. 常见误读（读本专用）

| 误读 | 正读 |
|------|------|
| 买家是星尘 SaaS 用户 | 买家是 **商家的顾客**；商小言付钱的通常是商家 |
| 小言是一个聊天 App | 是 **平台 + 多个应用**；故事共用一个昵称 |
| 澄光制造买商小言 | 澄光典型买 **修小言/内小言**；电商商家才买 **商小言** |
| 设备厂商 = 修小言租户 | **设备厂商** 常是 **渠道/白标方**；默认 **租户** 是 **设备客户企业**（澄光） |
| 商小言只有客服用 | 还有 **买家直连**（店铺窗/渠道入口）；买家不登录星尘，算力由商家租户承担，见 §5.6 |
| 买家直连 = 买家自己买星尘 | 买家 **不付** 星尘；**商家** 为店铺窗 AI 用量付费，见 §5.6.2 |
| 账小言是客服聊天 | 是 **结构化入账 / 对账 API**，聊天很弱 |
| 上了 AI 一定要星尘坐席 | 接管可 **客户 IT 自接**；坐席是 SLA 档位，不是默认 |
| 自建客服更简单 | **租户层简单**；深对接 WMS/ERP 后仍要 run/审批/幂等 |
